Deploying `chatflow-agent` swarms into production environments requires an architecture that balances non-blocking I/O, safe session concurrency, and operational resilience.

This guide outlines recommended deployment patterns, covering ASGI integration with FastAPI, SQLite storage considerations, Docker containerization, and health check monitoring.

## Architecture Blueprint

```text
Incoming Traffic (Clients / Webhooks)
          │
          ▼
Reverse Proxy (Nginx / Cloudflare / Traefik)
  ├── TLS Termination (HTTPS / WSS)
  ├── Request Timeout >= 120s
  └── Rate Limiting & DDoS Shield
          │
          ▼
ASGI Application Server (Uvicorn / Gunicorn)
  ├── Single-Process or Multi-Worker with Shared/Isolated Storage
  ├── FastAPI / Starlette Application
  └── chatflow-agent Runner
        ├── SQLiteSessionStore (WAL Mode) or Custom Distributed Store
        └── Concurrent Task Dispatching
```

## FastAPI ASGI Service Integration

`chatflow-agent` integrates seamlessly with FastAPI. By leveraging `runner.run_async()`, incoming HTTP requests execute concurrently on the event loop without blocking the server:

```python
import os
from contextlib import asynccontextmanager
from fastapi import FastAPI, HTTPException
from pydantic import BaseModel
from chatflow_agent import Agent, Runner
from chatflow_agent.core.memory import SQLiteSessionStore

class ChatRequest(BaseModel):
    session_id: str
    message: str

class ChatResponse(BaseModel):
    content: str
    agent: str

runner: Runner | None = None

@asynccontextmanager
async def lifespan(app: FastAPI):
    global runner
    store = SQLiteSessionStore("production_sessions.db", default_max_turns=40)
    agent = Agent(
        name="ProductionBot",
        model="gpt-4o",
        provider="openai",  # required in v0.3.4 for non-Gemini models
        instructions="Provide concise, accurate enterprise responses.",
    )
    runner = Runner(starting_agent=agent, session_store=store)
    yield

app = FastAPI(title="ChatFlow Enterprise API", lifespan=lifespan)

@app.post("/chat", response_model=ChatResponse)
async def chat_endpoint(payload: ChatRequest):
    if runner is None:
        raise HTTPException(status_code=503, detail="Runner service initializing.")
    try:
        result = await runner.run_async(
            session_id=payload.session_id,
            user_message=payload.message,
        )
        return ChatResponse(
            content=result.content,
            agent=result.active_agent_name,
        )
    except TimeoutError:
        raise HTTPException(status_code=504, detail="Inference turn timed out.")
    except Exception as err:
        raise HTTPException(status_code=500, detail="Internal agent execution failure.")

@app.get("/healthz")
async def health_check():
    """Health check endpoint for container orchestrators."""
    return {"status": "ok", "service": "chatflow-agent"}
```

## SQLite Concurrency Considerations

`SQLiteSessionStore` provides zero-infrastructure persistence with zero external service dependencies. Keep these points in mind when using it in production:

1. **WAL Mode (Write-Ahead Logging):** The store enables `PRAGMA journal_mode=WAL` and `busy_timeout=10000` on every connection automatically; there is nothing to configure.
2. **Event Loop Blocking:** In v0.3.4, SQLite calls run on the event loop thread, so a slow disk or a locked database delays every request handled by that loop. <VersionBadge version="0.4.0rc1" status="prerelease" /> offloads file-backed SQLite operations to worker threads.
3. **Per-Session Ordering:** In v0.3.4, concurrent requests for the same session are not serialized with `SQLiteSessionStore` (each call creates its own session object and lock). If a user can send messages faster than turns complete, queue them per session in your application.
4. **Process Isolation:** SQLite does not support safe high-concurrency writes across multiple independent OS processes (e.g. `gunicorn -w 8`). Run with a single worker process with high async concurrency (`uvicorn --workers 1`), or shard sessions by user identifier.

## Containerization with Docker

A production multi-stage Dockerfile minimizes image size and ensures security by running as a non-privileged user:

```dockerfile
# Multi-stage Dockerfile for chatflow-agent applications
FROM python:3.11-slim AS builder

WORKDIR /app

RUN apt-get update && apt-get install -y --no-install-recommends \
    build-essential \
    && rm -rf /var/lib/apt/lists/*

COPY requirements.txt .
RUN pip install --no-cache-dir --user -r requirements.txt

# Final Runtime Image
FROM python:3.11-slim AS runner

WORKDIR /app

# Run as non-root user
RUN addgroup --system appgroup && adduser --system --group appuser

COPY --from=builder /root/.local /home/appuser/.local
COPY --chown=appuser:appgroup . .

ENV PATH=/home/appuser/.local/bin:$PATH
ENV PYTHONUNBUFFERED=1

USER appuser

EXPOSE 8000

CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
```

## Reverse Proxy Configuration (Nginx)

LLM responses and multi-agent tool loops can take several seconds to complete. Ensure your reverse proxy does not terminate connections prematurely:

```nginx
server {
    listen 80;
    server_name agent.example.com;

    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection 'upgrade';
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # Generous timeouts for multi-agent inference turns
        proxy_connect_timeout 120s;
        proxy_send_timeout 120s;
        proxy_read_timeout 120s;
    }
}
```

## Production Readiness Checklist

| Category | Verification Item | Recommended Setting |
| :--- | :--- | :--- |
| **Networking** | Proxy Read Timeout | `timeout >= 120s` |
| **Resilience** | Request Timeouts | Configure provider or channel timeouts in v0.3.4; `turn_timeout` is available only in v0.4.0rc1 prerelease |
| **Persistence** | SQLite Workers | Run a single process per SQLite file; WAL is enabled automatically by the store |
| **Security** | Secrets Management | Injected via environment variables; never in code |
| **Monitoring** | Health Checks | `/healthz` endpoint returning HTTP 200 |
| **Process Model** | Concurrency | 1 worker process per container with asyncio concurrency |
