`chatflow-agent` is built upon six foundational architectural primitives that together enable lightweight, modular, and fault-tolerant conversational AI systems:

## What is a chatflow?

In `chatflow-agent`, a **chatflow** is the path a conversation develops as agents process messages, use tools, and transfer tasks to other agents. The `Runner` coordinates each turn, loads and persists session state, and invokes the active agent. Agents interpret the current request and decide whether to respond, use a tool, or hand off the conversation; tools perform the deterministic operations defined by the application.

The path develops from the user's requests and persisted [session state](/en/docs/v0.4/guides/sessions-state), rather than requiring a fixed sequence. The [tools guide](/en/docs/v0.4/guides/tools) and [handoffs guide](/en/docs/v0.4/guides/multi-agent-handoffs) explain those capabilities in detail. Channel integrations such as [Telegram](/en/docs/v0.4/integrations/telegram), [WhatsApp](/en/docs/v0.4/integrations/whatsapp), and [webhooks](/en/docs/v0.4/integrations/webhook) carry messages between external platforms and the runner.

**Conceptual example:** An application built with the library could let a user ask for an appointment. One agent identifies the specialty, another checks availability through an application-defined tool, and the application records the booking after the user confirms it. The appointment system and its business tools belong to the application; they are not built-in `chatflow-agent` features.

## 1. The Agent (`Agent`)

An `Agent` represents an autonomous actor with an explicit persona, system prompt instructions, a designated LLM model and engine, and access to tools or handoff peers.

```python
# [min-version: 0.3.0]
# [executable]
from chatflow_agent import Agent

# Static prompt instructions with target model
agent = Agent(
    name="TriageBot",
    instructions="You are the front desk concierge. Route questions to specialists.",
    model="gpt-4o",
)
```

### Dynamic Instructions

Instructions can be a static string or a dynamic Python callable (`Callable[[], str]`). Dynamic instructions are evaluated at the beginning of each turn:

```python
# [min-version: 0.3.0]
# [executable]
from datetime import datetime
from chatflow_agent import Agent

def get_live_instructions() -> str:
    now = datetime.now().strftime("%Y-%m-%d %H:%M:%S")
    return f"You are a scheduling assistant. Current server time is {now}."

agent = Agent(
    name="ScheduleBot",
    instructions=get_live_instructions,
    model="gemini-2.5-flash",
)
```

## 2. The Execution Engine (`Runner`)

The `Runner` orchestrates the conversation lifecycle. It handles:

1. Loading session context and conversation history from the `SessionStore`.
2. Checkpointing the session's history, active agent, and metadata before executing the turn.
3. Invoking the model engine.
4. Parsing tool calls, executing the corresponding functions, and feeding results back to the model until a final response is generated.
5. Keeping the changes on success, or restoring the checkpoint if the turn raises, is cancelled, or reaches its `turn_timeout`.

Synchronous invocation, for scripts and CLI tools (no event loop running):

```python
from chatflow_agent import Agent, Runner, SessionStore

agent = Agent(
    name="Assistant",
    instructions="Concise scheduling assistant.",
    model="gpt-4o",
)

store = SessionStore()

runner = Runner(
    starting_agent=agent,
    session_store=store,
)

response = runner.run(
    session_id="user_123",
    user_message="Book a meeting tomorrow at 3 PM",
)
```

Asynchronous invocation, inside an event loop (web servers, bots, `asyncio` apps):

```python
# [min-version: 0.4.0rc1]
# [no-exec: requires real openai api key for live response]
import asyncio

from chatflow_agent import Agent, Runner

async def main() -> None:
    agent = Agent(
        name="Assistant",
        instructions="Concise scheduling assistant.",
        model="gpt-4o",
    )
    async with Runner(starting_agent=agent) as runner:
        response = await runner.run_async(
            session_id="user_123",
            user_message="Book a meeting tomorrow at 3 PM",
        )
        print(response.content)

asyncio.run(main())
```

<Callout type="info" title="turn_timeout in v0.4.0rc1">
  In <VersionBadge version="0.4.0rc1" status="prerelease" />, <code>Runner.run_async</code>{' '}
  introduces an optional <code>turn_timeout: float | None = None</code> keyword parameter (e.g.{' '}
  <code>turn_timeout=30.0</code>). If a turn exceeds the deadline, it is cancelled and rolls back
  state atomically.
</Callout>

## 3. Provider Engines (`Engines`)

All model communication in `chatflow-agent` is decoupled behind the `BaseEngine` interface. Engines communicate over asynchronous HTTP REST using `httpx`, eliminating the need for monolithic vendor client libraries:

- **`OpenAIEngine`**: Supports OpenAI models and any OpenAI-compatible API (Groq, DeepSeek, xAI Grok, Ollama, vLLM) via `base_url`.
- **`AnthropicEngine`**: Direct REST integration with Anthropic Claude models.
- **`GeminiEngine`**: Google Gemini integration. In <VersionBadge version="0.4.0rc1" status="prerelease" />, completely rewritten with native REST calls.

```python
from chatflow_agent import Agent, OpenAIEngine

# Universal OpenAI-compatible engine for custom or local endpoints
local_engine = OpenAIEngine(
    base_url="http://localhost:11434/v1",
    provider="ollama",
    api_key="ollama",
)

local_agent = Agent(
    name="LocalBot",
    instructions="You run locally via Ollama.",
    model="llama3.2:latest",
    engine=local_engine,
)
```

## 4. Deterministic Tools (`Tool` & `@tool`)

Tools give agents deterministic execution power. When decorated with `@tool`, `chatflow-agent` builds the parameter schema from the Python type annotations and default values. The tool description is the `description=` argument, or the function docstring when no description is given; docstring sections such as `Args:` are not parsed into per-parameter descriptions:

```python
# [min-version: 0.3.0]
# [executable]
from chatflow_agent import tool

@tool(name="fetch_user_profile", description="Fetch user metadata from internal database.")
def fetch_user_profile(user_id: str) -> dict[str, str]:
    """Retrieve user details."""
    return {"user_id": user_id, "tier": "enterprise", "status": "active"}
```

Both synchronous (`def`) and asynchronous (`async def`) tool functions are natively supported. Alternatively, you can use the `@agent.tool` decorator directly on an agent instance.

## 5. Resilient Memory & Concurrency (`SessionStore`)

`chatflow-agent` treats state persistence and concurrency safety as first-class citizens:

```python
from chatflow_agent import SQLiteSessionStore

# Persistent SQLite session store. default_max_turns is a sliding history
# window: it keeps the last 40 complete turns of each session.
store = SQLiteSessionStore(
    db_path="./chat_sessions.db",
    default_max_turns=40,
)
```

### The Transactional Rollback Guarantee

Prior to processing a turn, `Runner` checkpoints the session's history, active agent, and metadata. If an exception escapes the turn (for example a provider outage), the turn is cancelled, or `turn_timeout` triggers, the checkpoint is restored before the error is raised. Corrupted or partial turns therefore never poison the conversation history.

### Event-Loop Protection & Concurrency Shields

- **Thread-Pool Offloading:** File-backed SQLite I/O runs inside the store's dedicated worker threads, preventing file system locks from blocking Python's asyncio event loop. `":memory:"` stores stay on the event loop.
- **Session Locking:** Turns of the same session are serialized (per store and event loop, for both `SessionStore` and `SQLiteSessionStore`); simultaneous requests for one session wait for the lock.
- **Reentrancy Guard (`ReentrantTurnError`):** Starting a turn for a session from code started by that session's running turn (a tool, or a task or thread it spawns) raises `ReentrantTurnError` instead of deadlocking. Use `Runner.spawn_turn()` to queue a follow-up turn.

## 6. Multi-Agent Handoffs (`Handoffs`)

Multi-agent swarms delegate tasks dynamically using declarative handoffs. When an agent declares a peer in `handoffs=[...]`, `chatflow-agent` synthesizes a transfer tool named after the peer's `name`, transliterated to ASCII, lowercased, and sanitized: a peer named `BillingAgent` becomes `transfer_to_billingagent`:

```python
from chatflow_agent import Agent, Runner

# Specialist Agent
billing_agent = Agent(
    name="BillingAgent",
    instructions="You specialize in invoices, receipts, and refund requests.",
    model="gpt-4o",
)

# Frontline Triage Agent
triage_agent = Agent(
    name="TriageAgent",
    instructions="Greet users. Transfer billing issues to BillingAgent.",
    model="gpt-4o",
    handoffs=[billing_agent],
)

runner = Runner(starting_agent=triage_agent)

# Execute turn with handoff
response = runner.run(
    session_id="user_billing_query",
    user_message="I need a copy of my invoice from last month.",
)

print(f"Responding agent: {response.active_agent_name}")
print(f"Message content: {response.content}")
```

The final responding agent is visible via `response.active_agent_name`. Transfers within one turn are capped by `Runner(max_handoffs_per_turn=5)`; there is no separate cycle detection.
