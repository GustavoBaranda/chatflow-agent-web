The `Runner` is the execution engine of **chatflow-agent**. It drives the multi-turn conversation loop, resolves LLM engines, coordinates tool executions, orchestrates autonomous handoffs, and enforces transactional state safety.

Applications interact with `Runner` as the primary interface: your code passes a `session_id` and a user message, and `Runner` executes the dialogue turn to completion, returning a typed `AgentResponse`.

---

## Constructor & Parameters

```python
from chatflow_agent import Agent, OpenAIEngine, Runner
from chatflow_agent.core.memory import SessionStore

starting_agent = Agent(name="Greeter", instructions="Greet users warmly.", model="gpt-4o")
memory_store = SessionStore()
engine = OpenAIEngine()

runner = Runner(
    starting_agent=starting_agent,
    session_store=memory_store,
    engine=engine,
    max_handoffs_per_turn=5,
    max_tool_iterations=10,
)
```

### Complete Parameter Reference

| Parameter | Type | Default | Description |
| :--- | :--- | :--- | :--- |
| `starting_agent` | `Agent` | *Required* | The root agent assigned to handle initial turns for newly created sessions. |
| `session_store` | `BaseSessionStore \| SessionStore \| None` | `SessionStore()` | Storage backend for conversation history and active agent pointers. |
| `engine` | `BaseEngine \| None` | `GeminiEngine(...)` | Default LLM generation engine used when an agent does not define its own. |
| `api_key` | `str \| None` | `None` | Default API key passed to the fallback engine if `engine` is omitted. |
| `max_handoffs_per_turn` | `int` | `5` | Maximum number of peer agent transfers permitted within a single turn. |
| `max_tool_iterations` | `int` | `10` | Maximum number of model-tool reasoning loops allowed before forced termination. |

## Agent Tree Indexing

When initialized, the `Runner` recursively traverses `starting_agent` and every peer in its `handoffs` list, building an internal registry (`_agents_registry`). This ensures any destination agent can be resolved instantly during handoffs:

```python
# [min-version: 0.3.0]
# [executable]
from chatflow_agent import Agent, Runner

billing = Agent(name="Billing", instructions="Billing", model="gpt-4o")
support = Agent(name="Support", instructions="Support", handoffs=[billing], model="gpt-4o")

runner = Runner(starting_agent=support)
# Both Support and Billing are automatically indexed
assert "Billing" in runner._agents_registry
```

If an agent is instantiated outside the root handoff graph, you can register it with `runner.register_agent(agent)`, but in v0.4.0rc1 that does not make it a handoff target: an agent can only hand off to peers in its own `handoffs`. Peers added later with `add_handoff()` are registered automatically on first use.

Indexing also validates names. In v0.4.0rc1, two distinct `Agent` instances with the same `name` anywhere in the handoff graph raise `ValueError` when the `Runner` is created (a breaking change from v0.3.4, which silently kept the first one).

## The Turn Execution Lifecycle

Every call to `runner.run_async()` follows a deterministic, transactionally protected sequence in v0.4.0rc1:

```
1. Session Lock Acquisition & Refresh
   ├── Refuse nested same-session turns (ReentrantTurnError).
   ├── Acquire the session's lock (shared per store, session ID, and event
   │   loop for both SessionStore and SQLiteSessionStore). Waiting here does
   │   not count against turn_timeout.
   └── session.refresh() reloads history, active agent, and metadata
       committed by earlier turns.

2. Checkpoint Creation & Metadata Merge
   ├── Checkpoint a copy of the history, the active agent, and a deep copy
   │   of the metadata.
   └── Merge the metadata passed to run_async() into the session.

3. Inbound Message Ingestion
   └── Append Message(role=Role.USER, content=user_message) to history.

4. Execution Loop (Up to max_tool_iterations)
   ├── A. Resolve active agent (from session.active_agent)
   ├── B. Resolve engine: agent.engine → agent.provider → agent.base_url
   │      → explicit Runner(engine=...) → model-name prefix
   │      → Runner's default GeminiEngine
   ├── C. Generate model turn via engine.generate_turn_async()
   ├── D. If Model Requests Tools:
   │      ├── Append Message(role=Role.MODEL, tool_calls=[...])
   │      ├── Execute tools / evaluate synthetic handoffs
   │      ├── If Handoff: swap active agent & check max_handoffs_per_turn
   │      └── Append Message(role=Role.TOOL, tool_results=[...])
   │      └── Continue loop for next agent evaluation
   └── E. If Final Text Generated:
          └── Append Message(role=Role.MODEL, content=final_text)
          └── Return AgentResponse

5. Exception / Cancellation / Timeout Handling
   └── On an exception, a cancellation, or turn_timeout, the checkpoint is
       restored (session.restore_history) before the error is raised.
```

## Transactional State Safety & Rollback

Network dropouts, rate limits, and tool exceptions can leave conversational state corrupted (such as an orphaned tool call without a corresponding tool result). In v0.4.0rc1, `Runner` makes each turn all-or-nothing:

* **Pre-turn Checkpoint:** After acquiring the lock and refreshing the session, `Runner` checkpoints a copy of the history, the active agent, and a deep copy of the metadata.
* **Automatic Rollback:** If an exception escapes the turn (for example a `ProviderError` or an unexpected tool error), the turn is cancelled (`asyncio.CancelledError`), or `turn_timeout` expires, `Runner` restores all three through `session.restore_history(...)` and then re-raises. With SQLite, a write that is already running is allowed to finish first, so the rollback never overlaps it.
* **Integrity Guarantee:** History, active agent, and metadata return to their state before the turn, so orphaned tool calls never reach subsequent provider requests. A rollback that fails is reported as an error, never as a success.
* **Limits:** A rollback cannot undo a tool's external side effects (payments, emails, API calls). A synchronous tool that is still running in a worker thread after a timeout keeps running; later turns of the same session wait for it.

### `run_async()` and `spawn_turn()` Parameters

| Method | Signature | Notes |
| :--- | :--- | :--- |
| `run_async` | `run_async(session_id, user_message, metadata=None, *, turn_timeout=None)` | `turn_timeout` is keyword-only and must be a positive finite number. It starts once the turn holds the session lock. On expiry the turn is rolled back and `TimeoutError` (`asyncio.TimeoutError`) is raised. |
| `run` | `run(session_id, user_message, metadata=None)` | Synchronous wrapper; raises `RuntimeError` if called from a running event loop. |
| `spawn_turn` | `spawn_turn(session_id, user_message, metadata=None) -> asyncio.Task[AgentResponse]` | Starts a turn as an independent task, for example a follow-up queued by a tool for its own session. It runs after the current turn ends; do not await it inside that turn (it would deadlock). |

```python
# [min-version: 0.4.0rc1]
# [no-exec: requires a live model provider]
import asyncio

from chatflow_agent import Agent, Runner

agent = Agent(name="Bot", instructions="Concise assistant", model="gemini-2.5-flash")

async def main() -> None:
    async with Runner(starting_agent=agent) as runner:
        try:
            response = await runner.run_async(
                session_id="user-1",
                user_message="Summarize the latest report.",
                turn_timeout=45.0,
            )
            print(response.content)
        except asyncio.TimeoutError:
            # The turn was rolled back; the session is as it was before.
            print("The turn took too long.")

asyncio.run(main())
```

## Async First vs. Synchronous Wrapper

`chatflow-agent` is natively built on `asyncio`.

### Asynchronous Execution (`run_async`)
The standard, non-blocking interface for web backends, background workers, and messaging webhooks:

```python
import asyncio
from chatflow_agent import Agent, Runner

async def main():
    agent = Agent(name="Bot", instructions="Concise assistant", model="gpt-4o")
    runner = Runner(starting_agent=agent)

    # Process turn asynchronously
    response = await runner.run_async(
        session_id="user-session-1",
        user_message="Hello!",
        metadata={"channel": "web"},
    )
    print(response.content)

asyncio.run(main())
```

### Synchronous Wrapper (`run`)
A convenience helper for scripts, interactive REPLs, and unit tests:

```python
# [min-version: 0.3.0]
# [no-exec: requires LLM engine for turn response]
from chatflow_agent import Agent, Runner

agent = Agent(name="Bot", instructions="Concise assistant", model="gpt-4o")
runner = Runner(starting_agent=agent)

# Runs event loop internally
response = runner.run(session_id="repl-1", user_message="Tell me a joke")
print(response.content)
```

<Callout type="warn" title="Synchronous run() in Active Event Loops">
Do not call <code>runner.run()</code> from inside an active asyncio event loop (such as inside a FastAPI async route handler or an active async task). Python prohibits nested event loop execution. In asynchronous environments, always use <code>await runner.run_async()</code>.
</Callout>

## Version Differences & Prerelease Features

The `Runner` execution engine includes major concurrency and performance upgrades across releases:

### Stable Release (`v0.3.4`)
* <VersionBadge version="0.3.4" status="stable" /> Core multi-agent loop with `max_handoffs_per_turn` and `max_tool_iterations`.
* Session locking via `session.lock` serializing messages per session.
* Checkpoint-based rollback on turn exceptions.

### Prerelease Enhancements (`v0.4.0rc1`)
* <VersionBadge version="0.4.0rc1" status="prerelease" /> **Connection Pooling (`async with runner:`):** Inside the scope, the Gemini requests the runner makes on that event loop share one pooled `httpx` client, closed when the scope exits. `OpenAIEngine` and `AnthropicEngine` still open a client per request attempt. `Runner.run()`, `TelegramChannel.run()`, and the `WhatsAppChannel` app open this scope automatically:
```python
# [min-version: 0.4.0rc1]
# [no-exec: illustrative async connection pool pattern]
from chatflow_agent import Agent, Runner

agent = Agent(name="Bot", instructions="Helper", model="gemini-2.5-flash")
runner = Runner(starting_agent=agent)

async def handle_requests():
    # Pools HTTP connections across multiple turns
    async with runner:
        res1 = await runner.run_async("s1", "First query")
        res2 = await runner.run_async("s1", "Second query")
```
* <VersionBadge version="0.4.0rc1" status="prerelease" /> **Reentrant Turn Prevention:** Calling `runner.run_async()` recursively on the same session (for example, if a tool invokes the runner on its own session) is detected and blocked with a `ReentrantTurnError`.
* <VersionBadge version="0.4.0rc1" status="prerelease" /> **Worker Thread Cancellation Tracking:** When an async turn is cancelled while a synchronous tool is executing in a thread, `chatflow-agent` tracks the worker thread to ensure the rollback never races with pending writes.
* <VersionBadge version="0.4.0rc1" status="prerelease" /> **Event Loop Guard on `run()`:** Calling synchronous `run()` inside an active event loop raises an explicit `RuntimeError` rather than hanging indefinitely.

## Common Pitfalls & Anti-Patterns

### 1. Re-instantiating `Runner` on Every Request
`Runner` indexes the agent tree and coordinates session caches. Create a singleton `Runner` per application lifecycle and share it across incoming request handlers:
```python
# [INCORRECT]: Recreating Runner per HTTP request re-indexes trees and resets connection pools
# def handle_post(msg):
#     runner = Runner(starting_agent=agent)
#     return runner.run("session", msg)

# [CORRECT]: Singleton Runner reused across requests
runner = Runner(starting_agent=agent)
async def handle_post(session_id: str, msg: str):
    return await runner.run_async(session_id, msg)
```

### 2. Calling Synchronous `run()` Inside Async Handlers
```python
# [INCORRECT]: Raises RuntimeError inside a running event loop
# async def api_endpoint(req):
#     return runner.run(req.session_id, req.message)

# [CORRECT]: Use await runner.run_async
async def api_endpoint(req_session_id: str, req_message: str):
    return await runner.run_async(req_session_id, req_message)
```

### 3. Ignoring the `AgentResponse` Metadata
`AgentResponse` returns more than just text. Inspect `active_agent_name`, `tool_calls_executed`, and `handoff` to power analytics and UI status indicators:
```python
response = runner.run(session_id="s1", user_message="Check order 505")
print(f"Handled by: {response.active_agent_name}")
print(f"Tools used: {response.tool_calls_executed}")
if response.handoff:
    print(f"Handoff target: {response.handoff.target_agent_name} (Reason: {response.handoff.reason})")
```
