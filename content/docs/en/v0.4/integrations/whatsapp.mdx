`WhatsAppChannel` connects multi-agent swarms directly to the official Meta WhatsApp Business Cloud API. Engineered for enterprise production environments, it includes an embedded FastAPI ASGI server, cryptographically verified webhooks, message deduplication, customer service window tracking, and phone number privacy masking.

## Installation

Install `chatflow-agent` with the `whatsapp` extra (`fastapi>=0.110.0`, `uvicorn>=0.29.0`):

```bash
pip install "chatflow-agent[whatsapp]"
```

## Architecture and Message Flow

```
Meta WhatsApp Cloud API
         |
         |  POST /webhook (Signed JSON + X-Hub-Signature-256)
         v
+-------------------------------------------------------------------+
|                         WhatsAppChannel                           |
|  1. HMAC SHA-256 Signature Verification (app_secret)              |
|  2. Message-ID Deduplication (session store, at-most-once)        |
|  3. Phone Number Masking in SDK Log Messages (_mask_phone)        |
|  4. Immediate HTTP 200 Acknowledgement                            |
+---------------------------------+---------------------------------+
                                  |
                        dispatch_async()
                                  |
                                  v
+---------------------------------+---------------------------------+
|                       chatflow-agent Runner                       |
|   - Session Lock & Queue Timeout (queue_timeout_seconds=120)      |
|   - Multi-Agent Turn Execution (llm_timeout_seconds=120)          |
|   - Tool Calling & State Persistence                              |
+---------------------------------+---------------------------------+
                                  |
                                  v
+---------------------------------+---------------------------------+
|                         Outbound Reply                            |
|   - 24h Customer Service Window Check                             |
|   - on_24h_window_expired Callback Hook                           |
|   - Outbound Chunking (split_message)                             |
|   - POST https://graph.facebook.com/v21.0/{phone_number_id}       |
+-------------------------------------------------------------------+
```

## Quickstart Webhook Setup

<Steps>
  <Step>
    ### Collect Meta Cloud API Credentials

    From your [Meta for Developers Dashboard](https://developers.facebook.com/):
    1. **Verify Token:** A custom secret token you define for initial webhook verification.
    2. **Access Token:** Permanent System User Access Token with `whatsapp_business_messaging` permissions.
    3. **Phone Number ID:** The ID of your registered WhatsApp Business test or production number.
    4. **App Secret:** Your Meta App Secret from App Settings &gt; Basic (used for HMAC signature validation).
  </Step>

  <Step>
    ### Initialize and Attach the Channel

```python
import os
from chatflow_agent import Agent, Runner
from chatflow_agent.channels import WhatsAppChannel
from chatflow_agent.core.memory import SQLiteSessionStore

# Define your agent
customer_service = Agent(
    name="CustomerService",
    instructions="Provide courteous, professional customer support.",
)

store = SQLiteSessionStore("whatsapp_sessions.db", dedup_ttl_hours=192)
runner = Runner(starting_agent=customer_service, session_store=store)

# Initialize WhatsApp Channel. Read every credential from the environment with
# no fallback value: a missing variable then fails at startup instead of
# running with a publicly known secret.
whatsapp = WhatsAppChannel(
    verify_token=os.environ["WHATSAPP_VERIFY_TOKEN"],
    access_token=os.environ["WHATSAPP_ACCESS_TOKEN"],
    phone_number_id=os.environ["WHATSAPP_PHONE_NUMBER_ID"],
    app_secret=os.environ["WHATSAPP_APP_SECRET"],
    verify_signature=True,
)

whatsapp.attach(runner)

if __name__ == "__main__":
    # Runs FastAPI ASGI server on port 8000
    whatsapp.run(host="0.0.0.0", port=8000)
```
  </Step>

  <Step>
    ### Configure Webhook URL in Meta Dashboard

    Point your Meta Webhook URL to `https://your-domain.com/webhook` and specify the matching Verify Token. Meta sends a `GET` request to verify the subscription, which `WhatsAppChannel` answers immediately.
  </Step>
</Steps>

## Security and Verification Standards

### Cryptographic HMAC SHA-256 Signature Validation

Meta signs every incoming POST webhook payload using your App Secret and attaches the signature in the `X-Hub-Signature-256` header.

<Callout type="warn" title="Fail-Closed Signature Policy">
If `verify_signature=True` (the default), omitting `app_secret` raises `ValueError` when the channel is constructed. After construction, a missing, malformed, or invalid `X-Hub-Signature-256` header is rejected with `HTTP 403 Forbidden`. Never disable signature verification in public production deployments.
</Callout>

### Request Validation and HTTP Status Codes

Before any turn runs, the `POST /webhook` endpoint applies these checks:

| Condition | Response |
| :--- | :--- |
| Missing `Content-Length` header | `411 Length Required` |
| Invalid `Content-Length` value, a body that is not valid JSON, or JSON that is not an object | `400 Bad Request` |
| `Content-Length` or body larger than `max_body_size` (default 1 MB) | `413` |
| Missing, malformed, or invalid `X-Hub-Signature-256` (with `verify_signature=True`) | `403 Forbidden` |
| Valid request, including duplicate deliveries and ignored `reaction` / `system` events | `200 OK` |

`GET /webhook` answers Meta's subscription challenge with a constant-time verify-token comparison, and `GET /health` returns a health status. The FastAPI documentation routes (`/docs`, `/redoc`, `/openapi.json`) are disabled unless you pass `enable_docs=True`.

Requests must carry a `Content-Length` header; check that any proxy in front of the server does not re-send the body with chunked transfer encoding.

### PII Protection & Phone Number Masking

`WhatsAppChannel` masks phone numbers in the SDK's own log messages by keeping the first four and last three characters. Meta sends the sender number as digits only:

```python
# Raw incoming phone: "14155552671"
# Logged output:      "1415***671"
```

Masking applies only to those log lines. The raw number still appears in:

* the webhook's JSON response body (`"sender"` field);
* the session ID and the turn metadata (`"phone"`), and therefore in the session store;
* the argument passed to `on_24h_window_expired`;
* Meta error responses, which are logged as received.

Treat logs, the session database, and any HTTP access logs as personal data.

## Concurrency, Timeouts, and Deadlines

Webhook acknowledgement is immediate; the turn then runs in the background with two separate limits:

| Parameter | Default | Purpose |
| :--- | :--- | :--- |
| `queue_timeout_seconds` | `120.0` | Maximum wait behind earlier turns of the same session (phone number). Must be a positive finite number. If it expires, the user receives `fallback_message` and the turn never runs, so it is not added to the history. |
| `llm_timeout_seconds` | `120.0` | Limit for the turn itself (model calls, tools, handoffs), starting once the turn holds the session. On expiry the turn is cancelled and rolled back, and `fallback_message` is sent. `None` or `inf` sets no limit. |

A reply can therefore take up to `queue_timeout_seconds + llm_timeout_seconds`. There is no setting that limits how many webhook turns run concurrently.

## 24-Hour Customer Care Window Tracking

Meta strictly limits free-form outbound messaging to within **24 hours of the user's last inbound message**. Attempting to send free-form text outside this window returns Meta API error code `131047`.

`WhatsAppChannel` includes a dedicated callback hook `on_24h_window_expired`. It is called with one argument, the recipient's phone number (unmasked). In v0.4.0rc1 it must be an `async def` function or a regular function; other callables that return a coroutine (such as an object with an `async __call__`) are not awaited. Exceptions raised by the hook are logged and do not stop the channel:

```python
async def handle_expired_window(phone_number: str) -> None:
    """Triggered when a reply cannot be delivered as a free-form message."""
    print(f"24h window closed for {phone_number}. Queuing template notification...")
    # Trigger approved WhatsApp Template message, CRM ticket, or email fallback

whatsapp = WhatsAppChannel(
    verify_token="token",
    access_token="token",
    phone_number_id="id",
    app_secret="secret",
    on_24h_window_expired=handle_expired_window,
)
```

## Message Deduplication (TTL)

Meta webhooks frequently resend duplicate HTTP deliveries if network latency delays acknowledgement. `WhatsAppChannel` records each message ID in the attached session store (`SessionStore` or `SQLiteSessionStore`) before queuing the turn. The TTL is the store's `dedup_ttl_hours` (default 192 hours, 8 days), for example `SQLiteSessionStore(..., dedup_ttl_hours=192)`. With SQLite, the check and the record are a single atomic statement (requires SQLite 3.24 or later). Duplicate webhook payloads receive immediate `HTTP 200` responses without re-executing agent turns.

<Callout type="warn" title="At-most-once delivery">
The message ID is recorded <em>before</em> the background turn runs. If the process crashes or restarts while that turn is running, the message is lost: Meta's retries of it are then discarded as duplicates.
</Callout>

`WhatsAppChannel` also accepts a `dedup_ttl_hours` argument in v0.4.0rc1, but it is stored and never used: only the session store's setting applies.

Message IDs are taken from the payload. A Meta-format message without an `id` gets an ID derived from Python's `hash()` of the message, which changes between process restarts. A generic (non-Meta) payload without an ID gets a random ID, so it is never treated as a duplicate.
