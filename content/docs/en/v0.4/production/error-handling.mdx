Building robust multi-agent systems requires structured fault tolerance. LLM provider outages, network timeouts, invalid tool arguments, and unexpected exceptions must be handled gracefully without corrupting conversation state.

`chatflow-agent` implements a layered recovery model: model-supplied tool arguments are validated at runtime with Pydantic (`validate_args=True` by default), tool errors are reported to the LLM as a sanitized error result so the turn can continue, and a turn that fails, is cancelled, or times out has its history, active agent, and metadata restored to their pre-turn state.

## SDK Exception Hierarchy

All exceptions in `chatflow-agent` inherit from `ChatFlowError`. This allows your application to distinguish between framework-level errors and standard Python exceptions.

```text
ChatFlowError (Base)
├── ConfigurationError (Invalid provider, endpoint, engine, or channel parameter) [v0.4.0]
├── DependencyError (Missing optional extra dependencies)
├── JsonCodecError (Non-JSON-serializable object in session metadata or strict JSON codec) [v0.4.0]
├── ToolExecutionError (Uncaught error during tool execution)
│   └── ToolArgumentValidationError (Runtime Pydantic tool argument failure) [v0.4.0]
├── ToolSchemaError (Union annotation with an unmappable member) [v0.4.0]
├── AgentHandoffError (Unknown or unauthorized handoff target)
├── ProviderError (Sanitized LLM API status error, network failure, or timeout)
├── ReentrantTurnError (Nested same-session turn or reset from an active turn) [v0.4.0]
└── SessionDeletedError (Running turn commits or rolls back after session deletion) [v0.4.0]
```

### Exception Reference Table

| Exception Class | Inherits From | Raised When | Recovery Strategy |
| :--- | :--- | :--- | :--- |
| `ChatFlowError` | `Exception` | Base class for all SDK exceptions. | Catch at top-level request boundaries. |
| `ConfigurationError` <VersionBadge version="0.4.0" status="stable" /> | `ChatFlowError`, `ValueError` | Invalid provider/engine setup, missing `api_key` on custom remote `base_url`, invalid `AnthropicEngine(max_tokens=...)`, or invalid channel limits. | Fix configuration parameters at startup. |
| `DependencyError` | `ChatFlowError` | An optional channel extra (e.g. `[telegram]`, `[whatsapp]`) is not installed. | Install the required extra via `pip install "chatflow-agent[extra]"`. |
| `JsonCodecError` <VersionBadge version="0.4.0" status="stable" /> | `ChatFlowError` | Session `metadata` contains an object that cannot be serialized to JSON (`datetime`, `date`, and `time` are supported automatically as ISO-8601). | Store only JSON-serializable values in `metadata`. |
| `ToolExecutionError` | `ChatFlowError` | A tool function raises an uncaught exception during execution. | Inside a turn, `Runner` logs it with a `trace_id` and returns a sanitized `ToolResult(is_error=True)` to the model. |
| `ToolArgumentValidationError` <VersionBadge version="0.4.0" status="stable" /> | `ToolExecutionError` | Model-supplied or caller-supplied tool arguments fail runtime Pydantic validation (`validate_args=True`). | Caught by `Runner` during turns and reported as a tool error so the LLM can self-correct; or pass `validate_args=False` to opt out. |
| `ToolSchemaError` <VersionBadge version="0.4.0" status="stable" /> | `ChatFlowError` | A tool is created with a union annotation containing a member with no concrete schema mapping (e.g., `CustomClass \| None` or `int \| datetime`). | `AgentHandoffError` | `ChatFlowError` | The handoff target does not exist or is not declared in the current agent's `handoffs`. Exceeding `max_handoffs_per_turn` does not raise: it adds an error tool result instead. | Verify handoff targets. |
| `ProviderError` | `ChatFlowError` | Upstream model provider returns an HTTP error code (e.g. 429, 500, 503). Secrets are redacted and raw `httpx`/`JSONDecodeError` `__cause__` chains are suppressed. | Implement exponential backoff or failover to a fallback engine. |
| `ReentrantTurnError` <VersionBadge version="0.4.0" status="stable" /> | `ChatFlowError`, `RuntimeError` | Code started by a running turn starts another turn or reset for the same session. | Use `Runner.spawn_turn()` to queue a follow-up turn. |
| `SessionDeletedError` <VersionBadge version="0.4.0" status="stable" /> | `ChatFlowError` | A running turn stores or rolls back state after its session was deleted. | Notify the user to restart the workflow; a later turn starts a new, empty session. |

## Runtime Tool Argument Validation & Autonomous Self-Correction

In `v0.4.0`, tools validate model-supplied arguments against their Python type hints via Pydantic (`validate_args=True` by default) before calling the function. If validation fails (raising `ToolArgumentValidationError`) or if the tool body itself raises an exception, `Runner` catches the failure and returns a structured error to the model instead of crashing the turn:

```python
import logging
from chatflow_agent import Agent, Runner, tool

logger = logging.getLogger("app.tools")

@tool
def process_refund(order_id: str, amount: float) -> str:
    """Issue a refund for an order.

    Args:
        order_id: Order identifier formatted as ORD-XXXX.
        amount: Positive monetary value to refund.
    """
    if not order_id.startswith("ORD-"):
        raise ValueError("Invalid order format. Order ID must begin with 'ORD-'.")
    if amount <= 0:
        raise ValueError("Refund amount must be strictly greater than 0.")
    return f"Refund of ${amount:.2f} processed for order {order_id}."

agent = Agent(
    name="RefundBot",
    model="gpt-4o",
    tools=[process_refund],
    instructions="Process refunds accurately. If an order ID format is invalid, clarify with the user.",
)

runner = Runner(starting_agent=agent)
```

### What Happens During Execution

1. The model invokes `process_refund(order_id="12345", amount=50.0)`.
2. `process_refund` raises `ValueError: Invalid order format. Order ID must begin with 'ORD-'.`.
3. `Runner` assigns a unique `trace_id` (UUID4) and appends a `ToolResult`:
   ```json
   {
     "tool_call_id": "call_abc123",
     "name": "process_refund",
     "content": "Tool execution failed [trace_id: a8c2...]. Please try a different approach or inform the user.",
     "is_error": true
   }
   ```
4. The original exception is logged to `chatflow_agent.runner` with the same `trace_id`. The model receives only the generic `is_error=True` result and cannot see the exception text, so it can only retry differently or tell the user that the operation failed. To let the model explain a specific problem, have the tool return a user-safe message instead of raising.

<Callout type="info" title="Loop Limit Protection">
To prevent infinite retry loops where an agent repeatedly fails a tool call, `Runner` enforces `max_tool_iterations` (default: `10`). If the limit is reached without a final text response, the runner returns a controlled fallback message without hanging.
</Callout>

## Transactional Turn Rollback

Multi-agent turns frequently modify conversation history, hand off to specialists, and update session metadata. If an unrecoverable failure occurs mid-turn (such as a network disconnect or provider rate limit), leaving the session in a half-executed state would corrupt subsequent interactions.

`Runner` guarantees **checkpoint rollback** semantics:

```text
Turn Start
    ├── Capture Checkpoint: (history, active_agent, metadata)
    ├── Append Inbound User Message
    ├── Execute LLM Turns & Tools
    │     ├── Success: Commit final assistant response to SessionStore
    │     └── Failure / CancelledError: Restore (history, active_agent, metadata)
    └── Release Session Lock
```

### Rollback Example in Code

```python
import asyncio
from chatflow_agent import Agent, Runner
from chatflow_agent.exceptions import ProviderError

def build_resilient_runner(agent: Agent) -> Runner:
    """Configure a runner with bounded handoffs and tool iterations."""
    return Runner(
        starting_agent=agent,
        max_tool_iterations=6,
        max_handoffs_per_turn=3,
    )

async def execute_turn_with_recovery(
    runner: Runner,
    session_id: str,
    user_message: str,
) -> str:
    """Execute a turn with explicit exception handling and graceful fallback."""
    try:
        response = await runner.run_async(
            session_id=session_id,
            user_message=user_message,
        )
        return response.content
    except ProviderError as err:
        # State was automatically rolled back to before the turn
        return "Our AI inference service is temporarily degraded. Please retry in a few moments."
    except TimeoutError:
        # Turn timeout exceeded; checkpoint restored
        return "The request took too long to complete. Please try a simpler question."
    except Exception as err:
        return "An unexpected system error occurred. Our operations team has been notified."
```

## Turn Timeouts & Resource Boundaries

<VersionBadge version="0.4.0" status="stable" />

In `v0.4.0`, `Runner.run_async()` supports an explicit keyword-only `turn_timeout: float | None = None` parameter (in seconds). The synchronous wrapper `Runner.run(session_id, user_message, metadata=None)` does **not** accept `turn_timeout`. Unlike generic request timeouts, `turn_timeout` begins counting only **after** the call acquires the session lock, ensuring queued turns do not expire prematurely while waiting behind earlier turns:

```python
# [min-version: 0.4.0]
# [no-exec: illustrative turn timeout call]
# Limits the turn execution to 45 seconds once lock is acquired
response = await runner.run_async(
    session_id="customer-1029",
    user_message="Analyze this quarterly financial audit report...",
    turn_timeout=45.0,
)
```

If `turn_timeout` expires:
1. The turn is cancelled. If one of its SQLite writes is running, it is allowed to finish first, so the `TimeoutError` can arrive later than the deadline.
2. A synchronous tool cannot be interrupted: its worker thread keeps running in the background, and later turns of the same session wait for it before acquiring the session lock.
3. The conversation history, active agent, and metadata roll back to the pre-turn checkpoint.
4. `asyncio.TimeoutError` is raised to the caller.

## Best Practices Checklist

- **Catch `ChatFlowError`:** Intercept framework exceptions before letting them propagate to HTTP handlers.
- **Set Bounded Iterations:** Never set `max_tool_iterations` or `max_handoffs_per_turn` to unbounded values.
- **Return Meaningful Tool Errors:** The model never sees the text of an exception raised by a tool, only a generic error with a `trace_id`. If the model should react to a specific problem (for example a malformed order ID), have the tool **return** a short, user-safe error message instead of raising.
- **Log Correlation IDs:** Capture the `trace_id` generated in `Runner` logs to correlate customer error reports with internal trace logs.
