`chatflow-agent` está construido sobre seis primitivas arquitectónicas fundamentales que en conjunto permiten desarrollar sistemas de IA conversacional ligeros, modulares y tolerantes a fallos:

## ¿Qué es un chatflow?

En `chatflow-agent`, llamamos **chatflow** al recorrido que desarrolla una conversación mientras los agentes procesan mensajes, usan herramientas y transfieren tareas a otros agentes. El `Runner` coordina cada turno, carga y conserva el estado de la sesión e invoca al agente activo. Los agentes interpretan la consulta actual y deciden si responden, usan una herramienta o transfieren la conversación; las herramientas ejecutan las operaciones deterministas definidas por la aplicación.

El recorrido se desarrolla según las consultas del usuario y el [estado persistente de la sesión](/es/docs/v0.3/guides/sessions-state), sin exigir una secuencia fija. Las guías de [herramientas](/es/docs/v0.3/guides/tools) y [handoffs](/es/docs/v0.3/guides/multi-agent-handoffs) explican esas capacidades en detalle. Las integraciones de canales, como [Telegram](/es/docs/v0.3/integrations/telegram), [WhatsApp](/es/docs/v0.3/integrations/whatsapp) y [webhooks](/es/docs/v0.3/integrations/webhook), transportan mensajes entre plataformas externas y el runner.

**Ejemplo conceptual:** Una aplicación construida con la librería podría permitir que un usuario consulte por un turno. Un agente identifica la especialidad, otro consulta la disponibilidad mediante una herramienta definida por la aplicación y la aplicación registra la reserva después de que el usuario la confirma. El sistema de turnos y sus herramientas de negocio pertenecen a la aplicación; no son funcionalidades incorporadas de `chatflow-agent`.

## 1. El Agente (`Agent`)

Un `Agent` representa un actor autónomo con una identidad definida, instrucciones de sistema (system prompt), un modelo y motor LLM asignado, y acceso a herramientas o pares de transferencia (handoffs).

```python
# [min-version: 0.3.0]
# [executable]
from chatflow_agent import Agent

# Instrucciones estáticas con modelo objetivo.
# En v0.3.4, los modelos que no son de Gemini necesitan un provider (o engine) explícito.
agent = Agent(
    name="TriageBot",
    instructions="You are the front desk concierge. Route questions to specialists.",
    model="gpt-4o",
    provider="openai",
)
```

### Instrucciones Dinámicas

Las instrucciones pueden ser una cadena estática o un ejecutable de Python dinámico (`Callable[[], str]`). Las instrucciones dinámicas se evalúan al inicio de cada turno:

```python
# [min-version: 0.3.0]
# [executable]
from datetime import datetime
from chatflow_agent import Agent

def get_live_instructions() -> str:
    now = datetime.now().strftime("%Y-%m-%d %H:%M:%S")
    return f"You are a scheduling assistant. Current server time is {now}."

agent = Agent(
    name="ScheduleBot",
    instructions=get_live_instructions,
    model="gemini-2.5-flash",
)
```

<Callout type="info" title="Validación de Identidad en Enjambres en v0.4.0rc1">
  En <VersionBadge version="0.4.0rc1" status="prerelease" />, el <code>Runner</code> valida
  estrictamente que todos los agentes dentro de un enjambre posean atributos <code>name</code>{' '}
  distintos, generando un <code>ValueError</code> si se detectan nombres duplicados para evitar
  colisiones en la síntesis de herramientas.
</Callout>

## 2. El Motor de Ejecución (`Runner`)

El `Runner` orquesta el ciclo de vida de la conversación. Se encarga de:

1. Cargar el contexto de la sesión y el historial de conversación desde el `SessionStore`.
2. Registrar la longitud del historial antes de procesar el turno.
3. Invocar el motor del modelo correspondiente.
4. Procesar las llamadas a herramientas, ejecutar las funciones y devolver los resultados al modelo hasta obtener la respuesta final.
5. Conservar los cambios exitosos o truncar el historial cuando una excepción ordinaria no controlada escapa del turno.

Invocación síncrona, para scripts y herramientas CLI (sin un bucle de eventos en ejecución):

```python
from chatflow_agent import Agent, Runner, SessionStore

agent = Agent(
    name="Assistant",
    instructions="Concise scheduling assistant.",
    model="gpt-4o",
    provider="openai",
)

store = SessionStore()

runner = Runner(
    starting_agent=agent,
    session_store=store,
)

response = runner.run(
    session_id="user_123",
    user_message="Book a meeting tomorrow at 3 PM",
)
```

Invocación asíncrona, dentro de un bucle de eventos (servidores web, bots, aplicaciones `asyncio`):

```python
import asyncio

from chatflow_agent import Agent, Runner

async def main() -> None:
    agent = Agent(
        name="Assistant",
        instructions="Concise scheduling assistant.",
        model="gpt-4o",
        provider="openai",
    )
    runner = Runner(starting_agent=agent)
    response = await runner.run_async(
        session_id="user_123",
        user_message="Book a meeting tomorrow at 3 PM",
    )
    print(response.content)

asyncio.run(main())
```

<Callout type="info" title="turn_timeout en v0.4.0rc1">
  En <VersionBadge version="0.4.0rc1" status="prerelease" />, <code>Runner.run_async</code>{' '}
  introduce un parámetro opcional <code>turn_timeout: float | None = None</code> (por ejemplo,{' '}
  <code>turn_timeout=30.0</code>). Si un turno supera el tiempo límite, se cancela y revierte el
  estado de forma atómica.
</Callout>

## 3. Motores de Proveedores (`Engines`)

Toda la comunicación con modelos en `chatflow-agent` está desacoplada tras la interfaz `BaseEngine`. En v0.3.4, los motores compatibles con OpenAI y de Anthropic llaman a sus APIs REST con `httpx`, mientras que `GeminiEngine` usa el cliente `google-genai`:

- **`OpenAIEngine`**: Compatible con modelos de OpenAI y cualquier API compatible con OpenAI (Groq, DeepSeek, xAI Grok, Ollama, vLLM) mediante `base_url`.
- **`AnthropicEngine`**: Integración REST directa con modelos Claude de Anthropic.
- **`GeminiEngine`**: Integración con Google Gemini a través de `google-genai`. En <VersionBadge version="0.4.0rc1" status="prerelease" />, se reescribió para llamar a la API REST de Gemini con `httpx`.

```python
from chatflow_agent import Agent, OpenAIEngine

# Motor universal compatible con OpenAI para endpoints locales o personalizados
local_engine = OpenAIEngine(
    base_url="http://localhost:11434/v1",
    provider="ollama",
    api_key="ollama",
)

local_agent = Agent(
    name="LocalBot",
    instructions="You run locally via Ollama.",
    model="llama3.2:latest",
    engine=local_engine,
)
```

## 4. Herramientas Deterministas (`Tool` y `@tool`)

Las herramientas otorgan a los agentes capacidad de ejecución determinista. Al decorar una función con `@tool`, `chatflow-agent` construye el esquema de parámetros a partir de las anotaciones de tipos y los valores por defecto de Python. La descripción de la herramienta es el argumento `description=` o, si no se proporciona, el docstring de la función; las secciones del docstring como `Args:` no se procesan como descripciones por parámetro:

```python
# [min-version: 0.3.0]
# [executable]
from chatflow_agent import tool

@tool(name="fetch_user_profile", description="Fetch user metadata from internal database.")
def fetch_user_profile(user_id: str) -> dict[str, str]:
    """Retrieve user details."""
    return {"user_id": user_id, "tier": "enterprise", "status": "active"}
```

Se admiten de forma nativa tanto funciones síncronas (`def`) como asíncronas (`async def`). Alternativamente, puedes usar el decorador `@agent.tool` directamente sobre una instancia de agente.

## 5. Memoria Resiliente y Concurrencia (`SessionStore`)

`chatflow-agent` trata la persistencia de estado y la seguridad ante concurrencia como prioridades fundamentales:

```python
from chatflow_agent import SQLiteSessionStore

# Almacenamiento persistente en SQLite. default_max_turns es una ventana deslizante
# del historial: conserva los últimos 40 turnos completos de cada sesión.
store = SQLiteSessionStore(
    db_path="./chat_sessions.db",
    default_max_turns=40,
)
```

### Garantía Transaccional de Rollback

Antes de procesar un turno, la versión estable v0.3.4 registra la longitud actual del historial. Si una excepción ordinaria escapa del turno, `Runner` trunca `session.history` hasta esa longitud. No restaura `active_agent` ni los metadatos, y la cancelación mediante `asyncio.wait_for` no está cubierta por esta garantía.

### Protección del Bucle de Eventos y Bloqueos de Concurrencia

- **Bloqueo por Sesión en v0.3.4:** Los turnos que comparten el mismo `SessionContext` en memoria se serializan con un `asyncio.Lock`; las llamadas externas concurrentes esperan y no generan `ReentrantTurnError`. Es una garantía del bucle de eventos, no de seguridad entre hilos o procesos.
- <VersionBadge version="0.4.0rc1" status="prerelease" /> **Protecciones de la Prerelease:** El I/O
  de SQLite en archivo se descarga mediante `_run_blocking`, y `ReentrantTurnError` rechaza un turno
  anidado de la misma sesión iniciado desde código que ya se ejecuta dentro de ese turno. Las
  llamadas externas independientes siguen esperando en cola.

## 6. Handoffs Multi-Agente (`Handoffs`)

Los enjambres multi-agente delegan tareas dinámicamente mediante handoffs declarativos. Cuando un agente declara un par en `handoffs=[...]`, `chatflow-agent` sintetiza una herramienta de transferencia nombrada a partir del `name` del par, en minúsculas y saneado: un par llamado `BillingAgent` se convierte en `transfer_to_billingagent`:

```python
from chatflow_agent import Agent, Runner

# Agente especialista
billing_agent = Agent(
    name="BillingAgent",
    instructions="You specialize in invoices, receipts, and refund requests.",
    model="gpt-4o",
    provider="openai",
)

# Agente de triaje inicial
triage_agent = Agent(
    name="TriageAgent",
    instructions="Greet users. Transfer billing issues to BillingAgent.",
    model="gpt-4o",
    provider="openai",
    handoffs=[billing_agent],
)

runner = Runner(starting_agent=triage_agent)

# Ejecutar turno con transferencia automática
response = runner.run(
    session_id="user_billing_query",
    user_message="I need a copy of my invoice from last month.",
)

print(f"Responding agent: {response.active_agent_name}")
print(f"Message content: {response.content}")
```

El agente final que responde es visible a través de `response.active_agent_name`. Las transferencias dentro de un turno están limitadas por `Runner(max_handoffs_per_turn=5)`; no existe una detección de ciclos aparte.
