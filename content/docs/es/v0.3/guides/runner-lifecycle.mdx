El `Runner` es el motor de ejecución central de **chatflow-agent**. Impulsa el bucle conversacional de múltiples turnos, resuelve motores LLM, coordina la ejecución de herramientas, orquesta transferencias autónomas y garantiza la seguridad transaccional del estado.

Las aplicaciones interactúan con `Runner` como interfaz principal: tu código envía un `session_id` y un mensaje de usuario, y el `Runner` ejecuta el turno de diálogo hasta completarlo, retornando una respuesta tipada `AgentResponse`.

---

## Constructor y Parámetros

```python
from chatflow_agent import Agent, OpenAIEngine, Runner
from chatflow_agent.core.memory import SessionStore

starting_agent = Agent(name="Greeter", instructions="Greet users warmly.", model="gpt-4o", provider="openai")
memory_store = SessionStore()
engine = OpenAIEngine()

runner = Runner(
    starting_agent=starting_agent,
    session_store=memory_store,
    engine=engine,
    max_handoffs_per_turn=5,
    max_tool_iterations=10,
)
```

### Referencia Completa de Parámetros

| Parámetro | Tipo | Predeterminado | Descripción |
| :--- | :--- | :--- | :--- |
| `starting_agent` | `Agent` | *Obligatorio* | Agente raíz asignado para gestionar turnos iniciales en sesiones nuevas. |
| `session_store` | `BaseSessionStore \| SessionStore \| None` | `SessionStore()` | Backend de almacenamiento para el historial de conversación y punteros de agente activo. |
| `engine` | `BaseEngine \| None` | `GeminiEngine(...)` | Motor LLM predeterminado utilizado cuando un agente no define el suyo propio. |
| `api_key` | `str \| None` | `None` | Clave de API por defecto pasada al motor de respaldo si se omite `engine`. |
| `max_handoffs_per_turn` | `int` | `5` | Número máximo de transferencias entre agentes pares permitidas en un único turno. |
| `max_tool_iterations` | `int` | `10` | Límite máximo de iteraciones de razonamiento modelo-herramienta antes de forzar la terminación. |

## Indexación del Árbol de Agentes

Al inicializarse, el `Runner` recorre recursivamente el `starting_agent` y cada par en su lista `handoffs`, construyendo un registro interno (`_agents_registry`). Esto asegura que cualquier agente de destino pueda resolverse de forma instantánea durante las transferencias:

```python
# [min-version: 0.3.0]
# [executable]
from chatflow_agent import Agent, Runner

billing = Agent(name="Billing", instructions="Billing", model="gpt-4o", provider="openai")
support = Agent(name="Support", instructions="Support", handoffs=[billing], model="gpt-4o", provider="openai")

runner = Runner(starting_agent=support)
# Tanto Support como Billing quedan indexados automáticamente
assert "Billing" in runner._agents_registry
```

Si se instancia un agente fuera del grafo inicial de transferencias, regístralo explícitamente mediante `runner.register_agent(agent)`.

## El Ciclo de Vida de Ejecución del Turno

Cada llamada a `runner.run_async()` sigue esta secuencia en v0.3.4:

```
1. Recuperación de Sesión y Adquisición de Bloqueo
   └── Obtiene o crea la sesión; adquiere el session.lock de ese objeto de sesión.
       Con el SessionStore en memoria, esto serializa los turnos de una sesión.
       Con SQLiteSessionStore, cada llamada construye un objeto de sesión nuevo con
       su propio bloqueo, por lo que los turnos concurrentes de una sesión NO se serializan.

2. Creación del Punto de Control (Checkpoint)
   └── Registra checkpoint_len = len(session.history) (solo la longitud del historial).

3. Ingestión del Mensaje Entrante
   └── Añade Message(role=Role.USER, content=user_message) al historial.

4. Bucle de Ejecución (Hasta max_tool_iterations)
   ├── A. Resuelve el agente activo (desde session.active_agent)
   ├── B. Resuelve el motor: agent.engine → agent.provider → agent.base_url
   │      → runner.engine (siempre definido; GeminiEngine por defecto)
   │      Los prefijos del nombre del modelo nunca se alcanzan a través de un Runner en v0.3.4.
   ├── C. Genera el turno del modelo mediante engine.generate_turn_async()
   ├── D. Si el Modelo Solicita Herramientas:
   │      ├── Añade Message(role=Role.MODEL, tool_calls=[...])
   │      ├── Ejecuta herramientas / evalúa handoffs sintéticos
   │      ├── Si ocurre Handoff: cambia el agente activo y verifica max_handoffs_per_turn
   │      └── Añade Message(role=Role.TOOL, tool_results=[...])
   │      └── Continúa el bucle para la siguiente evaluación del agente
   └── E. Si se Genera Texto Final:
          └── Añade Message(role=Role.MODEL, content=final_text)
          └── Retorna AgentResponse

5. Gestión de Excepciones
   └── Si escapa una excepción ordinaria, session.rollback_to(checkpoint_len)
       trunca el historial. La cancelación no se gestiona (ver más abajo).
```

## Reversión del Historial ante Excepciones

Interrupciones de red, límites de cuota y fallos en herramientas pueden dejar el historial de conversación corrupto (por ejemplo, una llamada a herramienta huérfana sin su resultado correspondiente). En v0.3.4, el `Runner` protege el **historial de conversación** frente a excepciones ordinarias:

* **Punto de Control Previo al Turno:** Antes de añadir el mensaje de usuario, el `Runner` guarda `checkpoint_len = len(session.history)`.
* **Reversión Automática del Historial:** Si una excepción (una subclase de `Exception`, por ejemplo un `ProviderError` del motor) escapa del turno, el historial se trunca hasta el punto de control:

```python
try:
    # Lógica de ejecución del turno
    pass
except Exception:
    if hasattr(session, "rollback_to"):
        session.rollback_to(checkpoint_len)
    else:
        session.history = session.history[:checkpoint_len]
    raise
```
* **Qué se restaura:** solo se eliminan los mensajes añadidos durante el turno fallido, de modo que ninguna llamada a herramienta huérfana llega a la siguiente petición al proveedor.
* **Qué no se restaura en v0.3.4:**
  * Un cambio de agente activo realizado por un handoff anteriormente en el turno fallido se mantiene (con `SQLiteSessionStore` ya está escrito en la base de datos).
  * Los metadatos de la sesión no se restauran.
  * La cancelación (`asyncio.CancelledError`, lanzada por ejemplo por `asyncio.wait_for` al agotarse el tiempo) no es una `Exception`, por lo que un turno cancelado **no** se revierte: los mensajes que ya añadió permanecen en el historial.

La reversión completa del historial, el agente activo y los metadatos, incluso ante cancelación y `turn_timeout`, es una característica de <VersionBadge version="0.4.0rc1" status="prerelease" />.

## Asíncrono Nativo vs. Wrapper Síncrono

`chatflow-agent` está construido nativamente sobre `asyncio`.

### Ejecución Asíncrona (`run_async`)
La interfaz estándar no bloqueante para backends web, trabajadores en segundo plano y webhooks de mensajería:

```python
import asyncio
from chatflow_agent import Agent, Runner

async def main():
    agent = Agent(name="Bot", instructions="Concise assistant", model="gpt-4o", provider="openai")
    runner = Runner(starting_agent=agent)

    # Procesar turno asíncronamente
    response = await runner.run_async(
        session_id="user-session-1",
        user_message="Hello!",
        metadata={"channel": "web"},
    )
    print(response.content)

asyncio.run(main())
```

### Wrapper Síncrono (`run`)
Una utilidad para scripts, REPLs interactivos y pruebas unitarias:

```python
# [min-version: 0.3.0]
# [no-exec: requires LLM engine for turn response]
from chatflow_agent import Agent, Runner

agent = Agent(name="Bot", instructions="Concise assistant", model="gpt-4o", provider="openai")
runner = Runner(starting_agent=agent)

# Ejecuta el bucle de eventos internamente
response = runner.run(session_id="repl-1", user_message="Tell me a joke")
print(response.content)
```

<Callout type="warn" title="run() Síncrono en Bucles de Eventos Activos">
No invoques <code>runner.run()</code> dentro de un bucle de eventos asyncio activo (como dentro de una ruta asíncrona en FastAPI o una tarea asíncrona). En v0.3.4 la llamada falla con el <code>RuntimeError</code> genérico de asyncio ("asyncio.run() cannot be called from a running event loop"). En entornos asíncronos, utiliza siempre <code>await runner.run_async()</code>.
</Callout>

## Diferencias de Versión y Características de Pre-lanzamiento

El motor de ejecución `Runner` incluye mejoras sustanciales de concurrencia y rendimiento entre versiones:

### Versión Estable (`v0.3.4`)
* <VersionBadge version="0.3.4" status="stable" /> Bucle multi-agente central con `max_handoffs_per_turn` y `max_tool_iterations`.
* Bloqueo de sesión mediante `session.lock`: serializa los turnos de una sesión con el `SessionStore` en memoria (un único bucle de eventos); no con `SQLiteSessionStore`, que crea un nuevo objeto de sesión y un nuevo bloqueo en cada llamada.
* Reversión solo del historial cuando una excepción ordinaria escapa de un turno; sin reversión ante cancelación.
* Ejecución asíncrona directa mediante `await runner.run_async(...)`:

```python
# [no-exec: illustrative async request handler pattern]
from chatflow_agent import Agent, Runner

agent = Agent(name="Bot", instructions="Helper", model="gemini-2.5-flash")
runner = Runner(starting_agent=agent)

async def handle_requests():
    # En v0.3.x, ejecuta turnos asíncronos directamente sobre la instancia compartida de runner
    res1 = await runner.run_async("s1", "First query")
    res2 = await runner.run_async("s1", "Second query")
```

<Callout type="info" title="Nota de Pre-lanzamiento: Mejoras en v0.4.0rc1">
La gestión de conexiones HTTP compartidas mediante <code>async with runner:</code> (para peticiones a Gemini), la prevención de turnos reentrantes con <code>ReentrantTurnError</code>, la serialización por sesión para almacenes SQLite, la reversión completa del estado incluida la cancelación y el seguimiento de cancelación en hilos trabajadores se introducen en la versión de pre-lanzamiento <strong>v0.4.0rc1</strong>. En la versión estable v0.3.4, ejecuta los turnos directamente sobre la instancia compartida del runner.
</Callout>

## Errores Comunes y Anti-Patrones

### 1. Reinstanciar `Runner` en Cada Petición
`Runner` indexa el árbol de agentes y coordina cachés de sesión. Crea un único `Runner` singleton durante el ciclo de vida de la aplicación y compártelo entre los controladores de peticiones:
```python
# [INCORRECTO]: Recrear Runner en cada petición HTTP re-indexa el árbol de agentes en cada llamada
# def handle_post(msg):
#     runner = Runner(starting_agent=agent)
#     return runner.run("session", msg)

# [CORRECTO]: Runner singleton reutilizado entre peticiones
runner = Runner(starting_agent=agent)
async def handle_post(session_id: str, msg: str):
    return await runner.run_async(session_id, msg)
```

### 2. Invocar el Método Síncrono `run()` dentro de Controladores Asíncronos
```python
# [INCORRECTO]: Falla con RuntimeError dentro de un bucle de eventos en ejecución (v0.3.4 y v0.4.0rc1)
# async def api_endpoint(req):
#     return runner.run(req.session_id, req.message)

# [CORRECTO]: Utiliza await runner.run_async
async def api_endpoint(req_session_id: str, req_message: str):
    return await runner.run_async(req_session_id, req_message)
```

### 3. Ignorar los Metadatos de `AgentResponse`
`AgentResponse` proporciona mucho más que texto. Inspecciona `active_agent_name`, `tool_calls_executed` y `handoff` para alimentar telemetría y elementos de estado en tu interfaz de usuario:
```python
response = runner.run(session_id="s1", user_message="Check order 505")
print(f"Handled by: {response.active_agent_name}")
print(f"Tools used: {response.tool_calls_executed}")
if response.handoff:
    print(f"Handoff target: {response.handoff.target_agent_name} (Reason: {response.handoff.reason})")
```
