`chatflow-agent` está construido sobre seis primitivas arquitectónicas fundamentales que, en conjunto, hacen posible sistemas conversacionales de IA ligeros, modulares y tolerantes a fallos:

## ¿Qué es un chatflow?

En `chatflow-agent`, llamamos **chatflow** al recorrido que desarrolla una conversación mientras los agentes procesan mensajes, usan herramientas y transfieren tareas a otros agentes. El `Runner` coordina cada turno, carga y conserva el estado de la sesión e invoca al agente activo. Los agentes interpretan la consulta actual y deciden si responden, usan una herramienta o transfieren la conversación; las herramientas ejecutan las operaciones deterministas definidas por la aplicación.

El recorrido se desarrolla según las consultas del usuario y el [estado persistente de la sesión](/es/docs/v0.4/guides/sessions-state), sin exigir una secuencia fija. Las guías de [herramientas](/es/docs/v0.4/guides/tools) y [handoffs](/es/docs/v0.4/guides/multi-agent-handoffs) explican esas capacidades en detalle. Las integraciones de canales, como [Telegram](/es/docs/v0.4/integrations/telegram), [WhatsApp](/es/docs/v0.4/integrations/whatsapp) y [webhooks](/es/docs/v0.4/integrations/webhook), transportan mensajes entre plataformas externas y el runner.

**Ejemplo conceptual:** Una aplicación construida con la librería podría permitir que un usuario consulte por un turno. Un agente identifica la especialidad, otro consulta la disponibilidad mediante una herramienta definida por la aplicación y la aplicación registra la reserva después de que el usuario la confirma. El sistema de turnos y sus herramientas de negocio pertenecen a la aplicación; no son funcionalidades incorporadas de `chatflow-agent`.

## 1. El Agente (`Agent`)

Un `Agent` representa un actor autónomo con una personalidad explícita, instrucciones en el prompt del sistema, un modelo y motor de LLM asignado, y acceso a herramientas o agentes homólogos para transferencias (_handoffs_).

```python
# [min-version: 0.3.0]
# [executable]
from chatflow_agent import Agent

# Instrucciones estáticas de prompt con modelo objetivo
agent = Agent(
    name="TriageBot",
    instructions="You are the front desk concierge. Route questions to specialists.",
    model="gpt-4o",
)
```

### Instrucciones Dinámicas

Las instrucciones pueden ser una cadena estática o una función invocable de Python (`Callable[[], str]`). Las instrucciones dinámicas se evalúan al inicio de cada turno:

```python
# [min-version: 0.3.0]
# [executable]
from datetime import datetime
from chatflow_agent import Agent

def get_live_instructions() -> str:
    now = datetime.now().strftime("%Y-%m-%d %H:%M:%S")
    return f"You are a scheduling assistant. Current server time is {now}."

agent = Agent(
    name="ScheduleBot",
    instructions=get_live_instructions,
    model="gemini-2.5-flash",
)
```

<Callout type="info" title="Validación de Identidad en Enjambres en v0.4.0rc1">
  En <VersionBadge version="0.4.0rc1" status="prerelease" />, el <code>Runner</code> valida
  estrictamente que todos los agentes dentro de un enjambre posean atributos <code>name</code>{' '}
  distintos, lanzando un <code>ValueError</code> si se detectan nombres duplicados para prevenir
  colisiones en la generación de herramientas.
</Callout>

## 2. El Motor de Ejecución (`Runner`)

El `Runner` orquesta el ciclo de vida de la conversación. Es responsable de:

1. Cargar el contexto de la sesión y el historial de la conversación desde el `SessionStore`.
2. Crear un punto de control (_checkpoint_) del historial, el agente activo y los metadatos de la sesión antes de ejecutar el turno.
3. Invocar el motor del modelo.
4. Procesar las llamadas a herramientas, ejecutar las funciones correspondientes y retroalimentar los resultados al modelo hasta obtener una respuesta final.
5. Conservar los cambios si el turno tiene éxito, o restaurar el punto de control si el turno lanza una excepción, se cancela o alcanza su `turn_timeout`.

Invocación síncrona, para scripts y herramientas CLI (sin un bucle de eventos en ejecución):

```python
from chatflow_agent import Agent, Runner, SessionStore

agent = Agent(
    name="Assistant",
    instructions="Concise scheduling assistant.",
    model="gpt-4o",
)

store = SessionStore()

runner = Runner(
    starting_agent=agent,
    session_store=store,
)

response = runner.run(
    session_id="user_123",
    user_message="Book a meeting tomorrow at 3 PM",
)
```

Invocación asíncrona, dentro de un bucle de eventos (servidores web, bots, aplicaciones `asyncio`):

```python
# [min-version: 0.4.0rc1]
# [no-exec: requires real openai api key for live response]
import asyncio

from chatflow_agent import Agent, Runner

async def main() -> None:
    agent = Agent(
        name="Assistant",
        instructions="Concise scheduling assistant.",
        model="gpt-4o",
    )
    async with Runner(starting_agent=agent) as runner:
        response = await runner.run_async(
            session_id="user_123",
            user_message="Book a meeting tomorrow at 3 PM",
        )
        print(response.content)

asyncio.run(main())
```

<Callout type="info" title="turn_timeout en v0.4.0rc1">
  En <VersionBadge version="0.4.0rc1" status="prerelease" />, <code>Runner.run_async</code>{' '}
  introduce un parámetro opcional con nombre <code>turn_timeout: float | None = None</code> (por
  ejemplo, <code>turn_timeout=30.0</code>). Si un turno excede el plazo, se cancela y revierte el
  estado de forma atómica.
</Callout>

## 3. Motores de Proveedores (`Engines`)

Toda la comunicación con modelos en `chatflow-agent` está desacoplada tras la interfaz `BaseEngine`. Los motores se comunican mediante HTTP REST asíncrono con `httpx`, eliminando la necesidad de bibliotecas cliente pesadas de proveedores:

- **`OpenAIEngine`**: Compatible con modelos de OpenAI y cualquier API compatible con OpenAI (Groq, DeepSeek, xAI Grok, Ollama, vLLM) mediante `base_url`.
- **`AnthropicEngine`**: Integración directa por REST con modelos Claude de Anthropic.
- **`GeminiEngine`**: Integración con Google Gemini. En <VersionBadge version="0.4.0rc1" status="prerelease" />, reescrita completamente con llamadas REST nativas.

```python
from chatflow_agent import Agent, OpenAIEngine

# Motor universal compatible con OpenAI para endpoints personalizados o locales
local_engine = OpenAIEngine(
    base_url="http://localhost:11434/v1",
    provider="ollama",
    api_key="ollama",
)

local_agent = Agent(
    name="LocalBot",
    instructions="You run locally via Ollama.",
    model="llama3.2:latest",
    engine=local_engine,
)
```

## 4. Herramientas Deterministas (`Tool` y `@tool`)

Las herramientas otorgan a los agentes poder de ejecución determinista. Al utilizar el decorador `@tool`, `chatflow-agent` construye el esquema de parámetros a partir de las anotaciones de tipo de Python y los valores por defecto. La descripción de la herramienta es el argumento `description=`, o el docstring de la función cuando no se proporciona una descripción; las secciones del docstring como `Args:` no se procesan para generar descripciones por parámetro:

```python
# [min-version: 0.3.0]
# [executable]
from chatflow_agent import tool

@tool(name="fetch_user_profile", description="Fetch user metadata from internal database.")
def fetch_user_profile(user_id: str) -> dict[str, str]:
    """Retrieve user details."""
    return {"user_id": user_id, "tier": "enterprise", "status": "active"}
```

Tanto las funciones síncronas (`def`) como las asíncronas (`async def`) son soportadas de forma nativa. Alternativamente, puedes utilizar el decorador `@agent.tool` directamente sobre una instancia de agente.

## 5. Memoria Resiliente y Concurrencia (`SessionStore`)

`chatflow-agent` trata la persistencia de estado y la seguridad ante concurrencia como ciudadanos de primer nivel:

```python
from chatflow_agent import SQLiteSessionStore

# Almacenamiento persistente en SQLite. default_max_turns es una ventana deslizante
# del historial: conserva los últimos 40 turnos completos de cada sesión.
store = SQLiteSessionStore(
    db_path="./chat_sessions.db",
    default_max_turns=40,
)
```

### La Garantía Transaccional de Reversión (Rollback)

Antes de procesar un turno, el `Runner` crea un punto de control del historial, el agente activo y los metadatos de la sesión. Si una excepción escapa del turno (por ejemplo, una caída del proveedor), el turno se cancela o se dispara `turn_timeout`, el punto de control se restaura antes de propagar el error. Por lo tanto, turnos corruptos o parciales nunca contaminan el historial de la conversación.

### Protección del Bucle de Eventos y Barreras de Concurrencia

- **Delegación a Grupo de Hilos:** La E/S de SQLite respaldada en archivo se ejecuta dentro de los hilos de trabajo dedicados del almacén, evitando que los bloqueos del sistema de archivos bloqueen el bucle de eventos asyncio de Python. Los almacenes `":memory:"` permanecen en el bucle de eventos.
- **Bloqueo de Sesión:** Los turnos de una misma sesión se serializan (por almacén y bucle de eventos, tanto para `SessionStore` como para `SQLiteSessionStore`); las peticiones simultáneas para una sesión esperan a que se libere el bloqueo.
- **Protección contra Reentrada (`ReentrantTurnError`):** Iniciar un turno para una sesión desde código iniciado por el turno en curso de esa misma sesión (una herramienta, o una tarea o hilo que esta lance) lanza `ReentrantTurnError` en lugar de provocar un interbloqueo. Utiliza `Runner.spawn_turn()` para encolar un turno posterior.

## 6. Handoffs Multi-Agente (`Handoffs`)

Los enjambres multi-agente delegan tareas dinámicamente mediante transferencias declarativas. Cuando un agente declara un par en `handoffs=[...]`, `chatflow-agent` sintetiza una herramienta de transferencia nombrada a partir del `name` del par, transliterado a ASCII, convertido a minúsculas y saneado: un par llamado `BillingAgent` se convierte en `transfer_to_billingagent`:

```python
from chatflow_agent import Agent, Runner

# Agente especialista
billing_agent = Agent(
    name="BillingAgent",
    instructions="You specialize in invoices, receipts, and refund requests.",
    model="gpt-4o",
)

# Agente de triaje inicial
triage_agent = Agent(
    name="TriageAgent",
    instructions="Greet users. Transfer billing issues to BillingAgent.",
    model="gpt-4o",
    handoffs=[billing_agent],
)

runner = Runner(starting_agent=triage_agent)

# Ejecutar turno con transferencia
response = runner.run(
    session_id="user_billing_query",
    user_message="I need a copy of my invoice from last month.",
)

print(f"Responding agent: {response.active_agent_name}")
print(f"Message content: {response.content}")
```

El agente que formuló la respuesta final está disponible a través de `response.active_agent_name`. Las transferencias dentro de un turno están limitadas por `Runner(max_handoffs_per_turn=5)`; no existe una detección de ciclos independiente.
