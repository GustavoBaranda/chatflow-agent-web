El despliegue de enjambres de `chatflow-agent` en entornos de producción exige una arquitectura que equilibre operaciones de E/S no bloqueantes, concurrencia segura de sesiones y resiliencia operativa.

Esta guía detalla los patrones de despliegue recomendados, abarcando la integración ASGI con FastAPI, consideraciones de almacenamiento con SQLite, contenerización con Docker y monitoreo mediante comprobaciones de salud (*health checks*).

## Modelo Arquitectónico

```text
Tráfico Entrante (Clientes / Webhooks)
          │
          ▼
Proxy Inverso (Nginx / Cloudflare / Traefik)
  ├── Terminación TLS (HTTPS / WSS)
  ├── Tiempo Límite de Petición >= 120s
  └── Limitación de Tasa y Protección DDoS
          │
          ▼
Servidor de Aplicaciones ASGI (Uvicorn / Gunicorn)
  ├── Proceso Único o Multi-Worker con Almacenamiento Compartido/Aislado
  ├── Aplicación FastAPI / Starlette
  └── chatflow-agent Runner
        ├── SQLiteSessionStore (Modo WAL) o Almacén Distribuido Personalizado
        └── Despacho Concurrente de Tareas
```

## Integración de Servicios ASGI con FastAPI

`chatflow-agent` se integra de forma transparente con FastAPI. Al aprovechar `runner.run_async()`, las peticiones HTTP entrantes se procesan concurrentemente en el bucle de eventos sin bloquear el servidor:

```python
import os
from contextlib import asynccontextmanager
from fastapi import FastAPI, HTTPException
from pydantic import BaseModel
from chatflow_agent import Agent, Runner
from chatflow_agent.core.memory import SQLiteSessionStore

class ChatRequest(BaseModel):
    session_id: str
    message: str

class ChatResponse(BaseModel):
    content: str
    agent: str

runner: Runner | None = None

@asynccontextmanager
async def lifespan(app: FastAPI):
    global runner
    store = SQLiteSessionStore("production_sessions.db", default_max_turns=40)
    agent = Agent(
        name="ProductionBot",
        model="gpt-4o",
        instructions="Provide concise, accurate enterprise responses.",
    )
    runner = Runner(starting_agent=agent, session_store=store)
    yield

app = FastAPI(title="ChatFlow Enterprise API", lifespan=lifespan)

@app.post("/chat", response_model=ChatResponse)
async def chat_endpoint(payload: ChatRequest):
    if runner is None:
        raise HTTPException(status_code=503, detail="Runner service initializing.")
    try:
        result = await runner.run_async(
            session_id=payload.session_id,
            user_message=payload.message,
        )
        return ChatResponse(
            content=result.content,
            agent=result.active_agent_name,
        )
    except TimeoutError:
        raise HTTPException(status_code=504, detail="Inference turn timed out.")
    except Exception as err:
        raise HTTPException(status_code=500, detail="Internal agent execution failure.")

@app.get("/healthz")
async def health_check():
    """Health check endpoint for container orchestrators."""
    return {"status": "ok", "service": "chatflow-agent"}
```

## Consideraciones de Concurrencia en SQLite

`SQLiteSessionStore` ofrece persistencia sin infraestructura externa ni dependencias de servicios adicionales. Al emplear SQLite en producción, aplica las siguientes configuraciones:

1. **Modo WAL (Write-Ahead Logging):** El modo de diario por defecto de SQLite bloquea el archivo completo durante las escrituras. El modo WAL permite lectores concurrentes mientras se ejecuta una escritura.
2. **Descarga a Hilos de Trabajo:** En `v0.4.0rc1`, `chatflow-agent` descarga las operaciones de base de datos SQLite a hilos de trabajo mediante `_run_blocking()`, asegurando que las operaciones de disco no bloqueen el bucle de eventos de asyncio.
3. **Aislamiento de Procesos:** SQLite no admite escrituras de alta concurrencia seguras entre múltiples procesos independientes del sistema operativo (ej. `gunicorn -w 8`). Ejecuta con un único proceso trabajador con alta concurrencia asíncrona (`uvicorn --workers 1`), o particiona las sesiones según el identificador de usuario.

## Contenerización con Docker

Un archivo Dockerfile multi-etapa para producción reduce el tamaño de la imagen y garantiza la seguridad ejecutándose bajo un usuario sin privilegios:

```dockerfile
# Multi-stage Dockerfile for chatflow-agent applications
FROM python:3.11-slim AS builder

WORKDIR /app

RUN apt-get update && apt-get install -y --no-install-recommends \
    build-essential \
    && rm -rf /var/lib/apt/lists/*

COPY requirements.txt .
RUN pip install --no-cache-dir --user -r requirements.txt

# Final Runtime Image
FROM python:3.11-slim AS runner

WORKDIR /app

# Run as non-root user
RUN addgroup --system appgroup && adduser --system --group appuser

COPY --from=builder /root/.local /home/appuser/.local
COPY --chown=appuser:appgroup . .

ENV PATH=/home/appuser/.local/bin:$PATH
ENV PYTHONUNBUFFERED=1

USER appuser

EXPOSE 8000

CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
```

## Configuración de Proxy Inverso (Nginx)

Las respuestas de los LLM y los bucles de herramientas multi-agente pueden tomar varios segundos en completarse. Asegúrate de que tu proxy inverso no interrumpa las conexiones prematuramente:

```nginx
server {
    listen 80;
    server_name agent.example.com;

    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection 'upgrade';
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # Generous timeouts for multi-agent inference turns
        proxy_connect_timeout 120s;
        proxy_send_timeout 120s;
        proxy_read_timeout 120s;
    }
}
```

## Lista de Verificación de Preparación para Producción

| Categoría | Elemento de Verificación | Configuración Recomendada |
| :--- | :--- | :--- |
| **Red** | Tiempo de Lectura del Proxy | `timeout >= 120s` |
| **Resiliencia** | Tiempo Límite de Turno | Configurar `turn_timeout=45.0` para prevenir turnos colgados |
| **Persistencia** | Modo de Diario en SQLite | `PRAGMA journal_mode=WAL;` |
| **Seguridad** | Gestión de Secretos | Inyectados vía variables de entorno; nunca en el código |
| **Monitoreo** | Comprobaciones de Salud | Endpoint `/healthz` retornando HTTP 200 |
| **Modelo de Procesos** | Concurrencia | 1 proceso worker por contenedor con concurrencia asyncio |
