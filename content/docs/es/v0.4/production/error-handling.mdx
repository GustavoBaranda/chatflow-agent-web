Construir sistemas multi-agente robustos requiere tolerancia a fallos estructurada. Caídas de proveedores de LLM, tiempos de espera de red, argumentos inválidos de herramientas y excepciones imprevistas deben manejarse ordenadamente sin corromper el estado de la conversación.

`chatflow-agent` implementa un modelo de recuperación por capas: los errores de herramientas se notifican al LLM como un resultado de error genérico para que el turno pueda continuar, mientras que un turno que falla, se cancela o agota su tiempo límite restaura su historial, su agente activo y sus metadatos al estado previo al turno (*rollback*).

## Jerarquía de Excepciones del SDK

Todas las excepciones en `chatflow-agent` heredan de `ChatFlowError`. Esto permite a tu aplicación distinguir entre errores propios del framework y excepciones generales de Python.

```text
ChatFlowError (Base)
├── DependencyError (Dependencias opcionales de extras ausentes)
├── ToolExecutionError (Error no capturado durante la ejecución de una herramienta)
├── ToolSchemaError (Anotación de unión con un miembro no mapeable) [v0.4.0rc1]
├── AgentHandoffError (Destino de transferencia desconocido o no autorizado)
├── ProviderError (Error de estado HTTP de API de LLM, fallo de red o tiempo de espera)
├── ReentrantTurnError (Turno anidado de la misma sesión iniciado desde un turno en curso) [v0.4.0rc1]
└── SessionDeletedError (Un turno en curso almacena un mensaje tras eliminarse su sesión) [v0.4.0rc1]
```

### Tabla de Referencia de Excepciones

| Clase de Excepción | Hereda de | Lanzada Cuando | Estrategia de Recuperación |
| :--- | :--- | :--- | :--- |
| `ChatFlowError` | `Exception` | Clase base para todas las excepciones del SDK. | Capturar en las fronteras de petición de nivel superior. |
| `DependencyError` | `ChatFlowError` | Falta instalar un extra opcional de canal (ej. `[telegram]`, `[whatsapp]`). | Instalar el extra requerido vía `pip install "chatflow-agent[extra]"`. |
| `ToolExecutionError` | `ChatFlowError` | Una función de herramienta lanza una excepción no capturada durante la ejecución. | Dentro de un turno, el `Runner` lo registra en el log y devuelve al modelo un `ToolResult(is_error=True)` genérico. |
| `ToolSchemaError` <VersionBadge version="0.4.0rc1" status="prerelease" /> | `ChatFlowError` | Se crea una herramienta con una anotación de unión que contiene un miembro sin mapeo de esquema. Los parámetros sin anotar están permitidos. | Corregir las firmas de tipos de la función en tiempo de desarrollo. |
| `AgentHandoffError` | `ChatFlowError` | El destino de la transferencia no existe o no está declarado en los `handoffs` del agente actual. Superar `max_handoffs_per_turn` no lanza la excepción: en su lugar añade un resultado de herramienta con error. | Verificar los destinos de transferencia. |
| `ProviderError` | `ChatFlowError` | El proveedor de modelos retorna un código de error HTTP (ej. 429, 500, 503). | Implementar retroceso exponencial o alternar a un motor de respaldo. |
| `ReentrantTurnError` <VersionBadge version="0.4.0rc1" status="prerelease" /> | `ChatFlowError`, `RuntimeError` | Código iniciado por un turno en curso inicia otro turno para la misma sesión. | Utilizar `Runner.spawn_turn()` para encolar un turno posterior. |
| `SessionDeletedError` <VersionBadge version="0.4.0rc1" status="prerelease" /> | `ChatFlowError` | Un turno en curso almacena un mensaje después de que su sesión SQLite haya sido eliminada. | Notificar al usuario para reiniciar el flujo; un turno posterior inicia una sesión nueva y vacía. |

## Autocorrección Autónoma de Herramientas

Cuando una herramienta registrada lanza una excepción, incluido un `TypeError` por argumentos que la función no acepta, `Runner` captura la falla y retorna un error estructurado al modelo en lugar de abortar el turno. v0.4.0rc1 no valida los argumentos de la herramienta contra el esquema antes de invocar la función:

```python
import logging
from chatflow_agent import Agent, Runner, tool

logger = logging.getLogger("app.tools")

@tool
def process_refund(order_id: str, amount: float) -> str:
    """Issue a refund for an order.

    Args:
        order_id: Order identifier formatted as ORD-XXXX.
        amount: Positive monetary value to refund.
    """
    if not order_id.startswith("ORD-"):
        raise ValueError("Invalid order format. Order ID must begin with 'ORD-'.")
    if amount <= 0:
        raise ValueError("Refund amount must be strictly greater than 0.")
    return f"Refund of ${amount:.2f} processed for order {order_id}."

agent = Agent(
    name="RefundBot",
    model="gpt-4o",
    tools=[process_refund],
    instructions="Process refunds accurately. If an order ID format is invalid, clarify with the user.",
)

runner = Runner(starting_agent=agent)
```

### Qué Sucede Durante la Ejecución

1. El modelo invoca `process_refund(order_id="12345", amount=50.0)`.
2. `process_refund` lanza `ValueError: Invalid order format. Order ID must begin with 'ORD-'.`.
3. `Runner` asigna un `trace_id` único (UUID4) y añade un `ToolResult`:
   ```json
   {
     "tool_call_id": "call_abc123",
     "name": "process_refund",
     "content": "Tool execution failed [trace_id: a8c2...]. Please try a different approach or inform the user.",
     "is_error": true
   }
   ```
4. La excepción original se registra en `chatflow_agent.runner` con el mismo `trace_id`. El modelo recibe únicamente el resultado genérico `is_error=True` y no puede ver el texto de la excepción, por lo que solo puede reintentar de otra forma o indicar al usuario que la operación falló. Para que el modelo pueda explicar un problema específico, haz que la herramienta devuelva un mensaje seguro para el usuario en lugar de lanzar una excepción.

<Callout type="info" title="Protección de Límite de Bucles">
Para evitar bucles infinitos de reintento donde un agente falla repetidamente una llamada a herramienta, `Runner` aplica `max_tool_iterations` (por defecto: `10`). Si se alcanza el límite sin una respuesta final de texto, el runner retorna un mensaje de respaldo controlado sin colgarse.
</Callout>

## Reversión Transaccional de Turnos (Checkpoint Rollback)

Los turnos multi-agente modifican con frecuencia el historial de conversación, delegan a especialistas y actualizan metadatos de sesión. Si ocurre un fallo irrecuperable a mitad del turno (como una desconexión de red o un límite de tasa del proveedor), dejar la sesión a medio ejecutar corrompería las interacciones posteriores.

`Runner` garantiza semánticas de **reversión por punto de control (checkpoint rollback)**:

```text
Inicio del Turno
    ├── Capturar Checkpoint: (history, active_agent, metadata)
    ├── Agregar Mensaje Entrante del Usuario
    ├── Ejecutar Turnos de LLM y Herramientas
    │     ├── Éxito: Confirmar respuesta final del asistente en SessionStore
    │     └── Fallo / CancelledError: Restaurar (history, active_agent, metadata)
    └── Liberar Bloqueo de Sesión
```

### Ejemplo de Reversión en Código

```python
import asyncio
from chatflow_agent import Agent, Runner
from chatflow_agent.exceptions import ProviderError

def build_resilient_runner(agent: Agent) -> Runner:
    """Configure a runner with bounded handoffs and tool iterations."""
    return Runner(
        starting_agent=agent,
        max_tool_iterations=6,
        max_handoffs_per_turn=3,
    )

async def execute_turn_with_recovery(
    runner: Runner,
    session_id: str,
    user_message: str,
) -> str:
    """Execute a turn with explicit exception handling and graceful fallback."""
    try:
        response = await runner.run_async(
            session_id=session_id,
            user_message=user_message,
        )
        return response.content
    except ProviderError as err:
        # El estado fue revertido automáticamente al estado previo al turno
        return "Our AI inference service is temporarily degraded. Please retry in a few moments."
    except TimeoutError:
        # Límite de tiempo del turno superado; checkpoint restaurado
        return "The request took too long to complete. Please try a simpler question."
    except Exception as err:
        return "An unexpected system error occurred. Our operations team has been notified."
```

## Tiempos Límite de Turno y Fronteras de Recursos

<VersionBadge version="0.4.0rc1" status="prerelease" />

A partir de `v0.4.0rc1`, `run_async` admite un parámetro explícito `turn_timeout` (en segundos). A diferencia de los tiempos límite genéricos de petición, `turn_timeout` comienza a contabilizarse únicamente **después** de que la llamada adquiere el bloqueo de sesión, garantizando que los turnos en cola no expiren prematuramente mientras esperan a turnos anteriores:

```python
# [min-version: 0.4.0rc1]
# [no-exec: illustrative turn timeout call]
# Limita la ejecución del turno a 45 segundos una vez adquirido el bloqueo
response = await runner.run_async(
    session_id="customer-1029",
    user_message="Analyze this quarterly financial audit report...",
    turn_timeout=45.0,
)
```

Si `turn_timeout` expira:
1. El turno se cancela. Si una de sus escrituras en SQLite está en curso, se permite que termine primero, por lo que el `TimeoutError` puede llegar más tarde que el plazo.
2. Una herramienta síncrona no puede interrumpirse: su hilo de trabajo sigue ejecutándose en segundo plano, y los turnos posteriores de la misma sesión esperan a que termine antes de adquirir el bloqueo de la sesión.
3. El historial de la conversación, el agente activo y los metadatos se revierten al punto de control previo al turno.
4. Se lanza `asyncio.TimeoutError` hacia el llamador.

## Lista de Buenas Prácticas

- **Capturar `ChatFlowError`:** Intercepta las excepciones del framework antes de propagarlas a los manejadores HTTP.
- **Configurar Iteraciones Acotadas:** Nunca configures `max_tool_iterations` o `max_handoffs_per_turn` en valores ilimitados.
- **Retornar Errores Descriptivos en Herramientas:** El modelo nunca ve el texto de una excepción lanzada por una herramienta, solo un error genérico con un `trace_id`. Si el modelo debe reaccionar ante un problema específico (por ejemplo, un ID de orden mal formado), haz que la herramienta **devuelva** un mensaje de error breve y seguro para el usuario en lugar de lanzar una excepción.
- **Registrar IDs de Correlación:** Captura el `trace_id` generado en los registros de `Runner` para correlacionar reportes de clientes con trazas internas.
