Los agentes de IA autónomos con capacidad para invocar herramientas, consultar bases de datos internas y comunicarse a través de canales de mensajería externos introducen desafíos de seguridad singulares. La defensa en profundidad exige blindar la frontera del LLM, proteger las credenciales contra filtraciones y aplicar una autorización rigurosa sobre los webhooks de canales.

`chatflow-agent` incorpora mecanismos de defensa directamente en sus motores centrales, ejecutores de runners e implementaciones de canales.

## Arquitectura Central de Seguridad

```text
Entrada No Confiable (Webhooks / Canales de Chat)
          │
          ▼
1. Seguridad de Transporte y Autenticación (HMAC SHA-256 / Bearer Tokens / Chequeo de Admin)
          │
          ▼
2. Bloqueo de Sesión y Protección contra Reentrancia (ReentrantTurnError / Bloqueo de Sesión)
          │
          ▼
3. Fronteras del Agente y Sandboxing de Herramientas (Validación / Tipado / Límites de Iteración)
          │
          ▼
4. Aislamiento de Credenciales y Control de Salida (ValueError en Host Personalizado / Sin Fugas de API Key)
```

## Protección de Credenciales y Control de Salida

Al conectarse a pasarelas o proxies de inferencia privados, los desarrolladores suelen anular `base_url`. Si un motor enviara credenciales oficiales de la nube (como `OPENAI_API_KEY`) a un endpoint arbitrario de terceros, los tokens secretos podrían filtrarse.

`chatflow-agent` aplica una protección automática de credenciales en `OpenAIEngine`:

```python
from chatflow_agent.core.engines.openai_compatible import OpenAIEngine

# [SEGURO] Endpoint oficial con variable de entorno
official_engine = OpenAIEngine(provider="openai")

# [SEGURO] Endpoint personalizado con token interno explícito
internal_engine = OpenAIEngine(
    base_url="https://gateway.internal.corp/v1",
    api_key="internal-bearer-token",
)

# [SEGURO] Inferencia local fuera de línea con clave ficticia
local_engine = OpenAIEngine(
    base_url="http://localhost:11434/v1",
    provider="ollama",
)
assert local_engine.api_key == "ollama"
```

<Callout type="warn" title="Protección Automática con ValueError">
Si especificas una `base_url` personalizada sin suministrar una `api_key` explícita, `OpenAIEngine` se niega a reutilizar `OPENAI_API_KEY` del entorno y lanza un `ValueError`. Esto previene la exfiltración accidental de credenciales hacia proxies no confiables.
</Callout>

## Protocolos de Seguridad en Canales

### Firmas HMAC SHA-256 en WhatsApp

Meta entrega los eventos de webhook de WhatsApp con un encabezado `X-Hub-Signature-256` calculado como `HMAC-SHA256(payload, app_secret)`.

`WhatsAppChannel` valida cada carga entrante antes de procesar el JSON o despachar turnos:

```python
import os
from chatflow_agent.channels import WhatsAppChannel

# Habilitar siempre la verificación de firmas en producción
channel = WhatsAppChannel(
    verify_token=os.environ.get("WHATSAPP_VERIFY_TOKEN", ""),
    access_token=os.environ.get("WHATSAPP_ACCESS_TOKEN", ""),
    phone_number_id=os.environ.get("WHATSAPP_PHONE_NUMBER_ID", ""),
    app_secret=os.environ.get("META_APP_SECRET", ""),
    verify_signature=True,  # Rechaza intentos no autenticados con HTTP 403
)
```

### Enmascaramiento Automático de Números Telefónicos

Los números telefónicos de clientes recibidos vía WhatsApp se clasifican como Información de Identificación Personal (PII). `WhatsAppChannel` enmascara automáticamente los números en la salida de registros (`+1415****71`) a través de su saneador interno `_mask_phone`, previniendo la fuga de PII hacia plataformas de monitoreo de logs.

### Administración en Chats Grupales de Telegram

En chats grupales, múltiples usuarios interactúan con el mismo bot. Permitir que cualquier miembro arbitrario ejecute `/reset` podría interrumpir flujos de trabajo activos para otros participantes.

`TelegramChannel` impone controles de autorización en `/reset`: consulta `get_chat_member` y permite el reinicio únicamente si el remitente posee el estatus de `creator` o `administrator` en el chat grupal.

## Inyección de Prompts y Fronteras de Herramientas

La inyección de prompts ocurre cuando entradas de usuarios no confiables inducen al LLM a eludir instrucciones del sistema o invocar herramientas no autorizadas.

Para mitigar riesgos de inyección de prompts:

1. **Principio de Menor Privilegio:** Concede a cada agente especializado exclusivamente las herramientas que requiere de forma estricta. Un `BillingAgent` no debe tener acceso a herramientas de eliminación de bases de datos o reinicio de servidores.
2. **Validación Determinista de Argumentos:** Valida todos los parámetros de herramientas frente a sugerencias explícitas de tipos y validaciones en tiempo de ejecución:

```python
from chatflow_agent import tool

@tool
def update_email(user_id: int, new_email: str) -> str:
    """Update a user's verified email address.

    Args:
        user_id: Numeric user identifier.
        new_email: Valid email address.
    """
    if "@" not in new_email or "." not in new_email:
        raise ValueError("Invalid email format.")
    # Ejecutar actualización
    return f"Email updated for user {user_id}."
```

3. **Triaje Multi-Agente:** Utiliza un agente de triaje inicial sin privilegios para clasificar solicitudes antes de derivarlas a agentes con permisos de escritura en bases de datos de producción.

## Seguridad en Reentrancia y Concurrencia

<VersionBadge version="0.4.0rc1" status="prerelease" />

A partir de `v0.4.0rc1`, `Runner` protege las sesiones frente a turnos concurrentes reentrantes:
- Si una herramienta ejecuta código que invoca `runner.run_async` sobre la misma sesión mientras el bloqueo está activo, `Runner` lanza `ReentrantTurnError`.
- Esto previene condiciones de carrera, recursiones infinitas y mutaciones concurrentes del historial.
