Los agentes de IA autónomos con capacidad para invocar herramientas, consultar bases de datos internas y comunicarse a través de canales de mensajería externos introducen desafíos de seguridad singulares. La defensa en profundidad exige blindar la frontera del LLM, proteger las credenciales contra filtraciones y aplicar una autorización rigurosa sobre los webhooks de canales.

`chatflow-agent` incorpora mecanismos de defensa directamente en sus motores centrales, ejecutores de runners e implementaciones de canales.

## Arquitectura Central de Seguridad

```text
Entrada No Confiable (Webhooks / Canales de Chat)
          │
          ▼
1. Autenticación de Entrada (HMAC SHA-256 de WhatsApp / Verify Token / Chequeo de Admin en Telegram)
          │
          ▼
2. Bloqueo de Sesión y Protección contra Reentrancia (Bloqueo de Sesión / ReentrantTurnError)
          │
          ▼
3. Fronteras del Agente (Herramientas Acotadas por Agente / Límites de Iteración y de Transferencias)
          │
          ▼
4. Aislamiento de Credenciales y Control de Salida (ValueError en Host Personalizado / Sin Fugas de API Key)
```

El SDK no aísla las herramientas en un sandbox: se ejecutan en el proceso de la aplicación con todos sus privilegios y, en v0.4.0rc1, los argumentos de herramientas proporcionados por el modelo se pasan a la función sin validación en tiempo de ejecución. La autenticación de entrada para canales personalizados, como los Bearer tokens, la implementa tu aplicación.

## Protección de Credenciales y Control de Salida

Al conectarse a pasarelas o proxies de inferencia privados, los desarrolladores suelen anular `base_url`. Si un motor enviara credenciales oficiales de la nube (como `OPENAI_API_KEY`) a un endpoint arbitrario de terceros, los tokens secretos podrían filtrarse.

`chatflow-agent` aplica una protección automática de credenciales en `OpenAIEngine`:

```python
from chatflow_agent.core.engines.openai_compatible import OpenAIEngine

# [SEGURO] Endpoint oficial con variable de entorno
official_engine = OpenAIEngine(provider="openai")

# [SEGURO] Endpoint personalizado con token interno explícito
internal_engine = OpenAIEngine(
    base_url="https://gateway.internal.corp/v1",
    api_key="internal-bearer-token",
)

# [SEGURO] Inferencia local fuera de línea: no se requiere clave. El motor usa
# OLLAMA_API_KEY si está definida; en caso contrario, la clave provisional "ollama".
local_engine = OpenAIEngine(
    base_url="http://localhost:11434/v1",
    provider="ollama",
)
```

<Callout type="warn" title="Protección Automática con ValueError">
Si especificas una `base_url` remota personalizada sin suministrar una `api_key` explícita, `OpenAIEngine` se niega a reutilizar `OPENAI_API_KEY` (o la clave de cualquier otro proveedor) del entorno y lanza un `ValueError`. Esto previene la exfiltración accidental de credenciales hacia proxies no confiables. Los hosts de loopback (`localhost`, `127.0.0.1`, `::1`, `0.0.0.0`) quedan exentos y reciben en su lugar una clave provisional. En v0.4.0rc1, `GeminiEngine` además nunca sigue redirecciones HTTP y elimina la clave de API de sus mensajes de error.
</Callout>

## Protocolos de Seguridad en Canales

### Firmas HMAC SHA-256 en WhatsApp

Meta entrega los eventos de webhook de WhatsApp con un encabezado `X-Hub-Signature-256` calculado como `HMAC-SHA256(payload, app_secret)`.

`WhatsAppChannel` valida cada carga entrante antes de procesar el JSON o despachar turnos:

```python
import os
from chatflow_agent.channels import WhatsAppChannel

# Habilitar siempre la verificación de firmas en producción
channel = WhatsAppChannel(
    verify_token=os.environ["WHATSAPP_VERIFY_TOKEN"],
    access_token=os.environ["WHATSAPP_ACCESS_TOKEN"],
    phone_number_id=os.environ["WHATSAPP_PHONE_NUMBER_ID"],
    app_secret=os.environ["WHATSAPP_APP_SECRET"],
    verify_signature=True,  # Las peticiones con firma ausente o inválida reciben HTTP 403
)
```

Con `verify_signature=True` (el valor predeterminado), construir el canal sin un `app_secret` lanza `ValueError`. Lee los secretos sin valores de respaldo: un marcador no vacío como `"secret"` superaría esa comprobación y permitiría a cualquiera que lo conozca falsificar peticiones firmadas.

### Enmascaramiento Automático de Números Telefónicos

Los números telefónicos de clientes recibidos vía WhatsApp son Información de Identificación Personal (PII). `WhatsAppChannel` enmascara los valores en sus propios mensajes de log conservando los cuatro primeros y los tres últimos caracteres de entrada; por ejemplo, el remitente de Meta `14155552671` se convierte en `1415***671`. El número sin procesar sigue apareciendo en la respuesta JSON del webhook (`"sender"`), en el ID de sesión y los metadatos almacenados por el almacén de sesiones, en el argumento que se pasa a `on_24h_window_expired` y en las respuestas de error de Meta, que se registran tal como se reciben. Las aplicaciones y las herramientas externas deben aplicar sus propias políticas de ocultación.

### Administración en Chats Grupales de Telegram

En chats grupales, múltiples usuarios interactúan con el mismo bot. Permitir que cualquier miembro arbitrario ejecute `/reset` podría interrumpir flujos de trabajo activos para otros participantes.

`TelegramChannel` impone controles de autorización en `/reset`: consulta `get_chat_member` y permite el reinicio únicamente si el remitente posee el estatus de `creator` o `administrator` en el chat grupal.

## Inyección de Prompts y Fronteras de Herramientas

La inyección de prompts ocurre cuando entradas de usuarios no confiables inducen al LLM a eludir instrucciones del sistema o invocar herramientas no autorizadas.

Para mitigar riesgos de inyección de prompts:

1. **Principio de Menor Privilegio:** Concede a cada agente especializado exclusivamente las herramientas que requiere de forma estricta. Un `BillingAgent` no debe tener acceso a herramientas de eliminación de bases de datos o reinicio de servidores.
2. **Valida los Argumentos Dentro de Cada Herramienta:** v0.4.0rc1 no valida ni convierte en tiempo de ejecución los argumentos proporcionados por el modelo; las sugerencias de tipo solo determinan el esquema que ve el modelo. Comprueba cada entrada dentro de la herramienta antes de actuar en consecuencia:

```python
from chatflow_agent import tool

@tool
def update_email(user_id: int, new_email: str) -> str:
    """Update a user's verified email address."""
    if not isinstance(user_id, int):
        raise ValueError("user_id must be an integer.")
    if "@" not in new_email or "." not in new_email:
        raise ValueError("Invalid email format.")
    # Ejecutar actualización
    return f"Email updated for user {user_id}."
```

3. **Triaje Multi-Agente:** Utiliza un agente de triaje inicial sin privilegios para clasificar solicitudes antes de derivarlas a agentes con permisos de escritura en bases de datos de producción.

## Seguridad en Reentrancia y Concurrencia

<VersionBadge version="0.4.0rc1" status="prerelease" />

A partir de `v0.4.0rc1`, `Runner` protege las sesiones frente a turnos reentrantes:
- Si código iniciado por un turno en curso (una herramienta, o una tarea o hilo que esta inicie: `create_task`, `gather`, `wait_for`, `TaskGroup`, `asyncio.to_thread`) invoca `runner.run_async` o `runner.run` para la misma sesión, `Runner` lanza `ReentrantTurnError` de inmediato en lugar de provocar un interbloqueo. Utiliza `Runner.spawn_turn()` para encolar un turno posterior.
- Las peticiones independientes para la misma sesión se serializan mediante el bloqueo de sesión (por instancia de almacén, ID de sesión y bucle de eventos).

Limitaciones conocidas en v0.4.0rc1:
- No se proporciona serialización entre instancias de almacén sobre el mismo archivo, entre procesos ni entre hilos que ejecutan sus propios bucles de eventos.
- Una herramienta que espera trabajo realizado por una tarea que no se inició desde el turno aún puede provocar un interbloqueo si ese trabajo ejecuta un turno de la misma sesión; esperar con await una tarea de `spawn_turn()` dentro del turno que la lanzó también provoca un interbloqueo.
- `clear_history()` y `delete()` (y, por tanto, el `/reset` de Telegram) no se coordinan con los turnos en curso más allá de las garantías de reversión y de `SessionDeletedError`.
