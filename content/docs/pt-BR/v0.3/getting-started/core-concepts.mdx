O `chatflow-agent` é construído sobre seis primitivas arquiteturais fundamentais que, juntas, viabilizam sistemas de IA conversacional leves, modulares e tolerantes a falhas:

## O que é um chatflow?

No `chatflow-agent`, chamamos de **chatflow** o percurso que uma conversa desenvolve enquanto os agentes processam mensagens, usam ferramentas e transferem tarefas para outros agentes. O `Runner` coordena cada turno, carrega e preserva o estado da sessão e invoca o agente ativo. Os agentes interpretam a solicitação atual e decidem se respondem, usam uma ferramenta ou transferem a conversa; as ferramentas executam as operações determinísticas definidas pela aplicação.

O percurso se desenvolve de acordo com as solicitações do usuário e o [estado persistente da sessão](/pt-BR/docs/v0.3/guides/sessions-state), sem exigir uma sequência fixa. Os guias de [ferramentas](/pt-BR/docs/v0.3/guides/tools) e [handoffs](/pt-BR/docs/v0.3/guides/multi-agent-handoffs) explicam esses recursos em detalhes. As integrações de canais, como [Telegram](/pt-BR/docs/v0.3/integrations/telegram), [WhatsApp](/pt-BR/docs/v0.3/integrations/whatsapp) e [webhooks](/pt-BR/docs/v0.3/integrations/webhook), transportam mensagens entre plataformas externas e o runner.

**Exemplo conceitual:** Uma aplicação construída com a biblioteca poderia permitir que um usuário solicitasse um agendamento. Um agente identifica a especialidade, outro consulta a disponibilidade por meio de uma ferramenta definida pela aplicação e a aplicação registra o agendamento depois que o usuário o confirma. O sistema de agendamento e suas ferramentas de negócio pertencem à aplicação; eles não são recursos integrados do `chatflow-agent`.

## 1. O Agente (`Agent`)

Um `Agent` representa um ator autônomo com persona explícita, instruções de prompt de sistema, um modelo e motor LLM designados, e acesso a ferramentas ou agentes parceiros para transferência (_handoff_).

```python
# [min-version: 0.3.0]
# [executable]
from chatflow_agent import Agent

# Instruções de prompt estáticas com modelo alvo.
# Na v0.3.4, modelos que não são Gemini precisam de um provider (ou engine) explícito.
agent = Agent(
    name="TriageBot",
    instructions="You are the front desk concierge. Route questions to specialists.",
    model="gpt-4o",
    provider="openai",
)
```

### Instruções Dinâmicas

As instruções podem ser uma string estática ou uma função chamável em Python (`Callable[[], str]`). Instruções dinâmicas são avaliadas no início de cada turno:

```python
# [min-version: 0.3.0]
# [executable]
from datetime import datetime
from chatflow_agent import Agent

def get_live_instructions() -> str:
    now = datetime.now().strftime("%Y-%m-%d %H:%M:%S")
    return f"You are a scheduling assistant. Current server time is {now}."

agent = Agent(
    name="ScheduleBot",
    instructions=get_live_instructions,
    model="gemini-2.5-flash",
)
```

<Callout type="info" title="Validação de Identidade de Enxame na v0.4.0rc1">
  Na versão <VersionBadge version="0.4.0rc1" status="prerelease" />, o <code>Runner</code> valida
  rigorosamente que todos os agentes em um enxame possuam atributos <code>name</code> distintos,
  levantando um <code>ValueError</code> caso nomes duplicados sejam detectados para evitar colisões
  na geração de ferramentas.
</Callout>

## 2. O Motor de Execução (`Runner`)

O `Runner` orquestra o ciclo de vida da conversa. Ele gerencia:

1. Carregamento do contexto da sessão e histórico de mensagens a partir do `SessionStore`.
2. Registro do tamanho do histórico antes de executar o turno.
3. Invocação do motor do modelo LLM.
4. Análise de chamadas de ferramentas (_tool calls_), execução das funções correspondentes e envio dos resultados de volta ao modelo até que a resposta final seja gerada.
5. Preservação das alterações bem-sucedidas ou truncamento do histórico quando uma exceção comum não tratada escapa do turno.

Invocação síncrona, para scripts e ferramentas de CLI (sem loop de eventos em execução):

```python
from chatflow_agent import Agent, Runner, SessionStore

agent = Agent(
    name="Assistant",
    instructions="Concise scheduling assistant.",
    model="gpt-4o",
    provider="openai",
)

store = SessionStore()

runner = Runner(
    starting_agent=agent,
    session_store=store,
)

response = runner.run(
    session_id="user_123",
    user_message="Book a meeting tomorrow at 3 PM",
)
```

Invocação assíncrona, dentro de um loop de eventos (servidores web, bots, aplicações `asyncio`):

```python
import asyncio

from chatflow_agent import Agent, Runner

async def main() -> None:
    agent = Agent(
        name="Assistant",
        instructions="Concise scheduling assistant.",
        model="gpt-4o",
        provider="openai",
    )
    runner = Runner(starting_agent=agent)
    response = await runner.run_async(
        session_id="user_123",
        user_message="Book a meeting tomorrow at 3 PM",
    )
    print(response.content)

asyncio.run(main())
```

<Callout type="info" title="turn_timeout na v0.4.0rc1">
  Na versão <VersionBadge version="0.4.0rc1" status="prerelease" />, o método{' '}
  <code>Runner.run_async</code> introduz o parâmetro opcional{' '}
  <code>turn_timeout: float | None = None</code> (por exemplo, <code>turn_timeout=30.0</code>). Se
  um turno exceder o tempo limite, ele é cancelado e o estado é revertido atomicamente.
</Callout>

## 3. Motores de Provedores (`Engines`)

Toda a comunicação com modelos no `chatflow-agent` é desacoplada através da interface `BaseEngine`. Na v0.3.4, os motores compatíveis com OpenAI e da Anthropic chamam suas APIs REST com `httpx`, enquanto o `GeminiEngine` usa o cliente `google-genai`:

- **`OpenAIEngine`**: Suporta modelos OpenAI e qualquer API compatível com OpenAI (Groq, DeepSeek, xAI Grok, Ollama, vLLM) através do parâmetro `base_url`.
- **`AnthropicEngine`**: Integração REST direta com modelos Claude da Anthropic.
- **`GeminiEngine`**: Integração com Google Gemini por meio do `google-genai`. Na versão <VersionBadge version="0.4.0rc1" status="prerelease" />, foi reescrito para chamar a API REST do Gemini com `httpx`.

```python
from chatflow_agent import Agent, OpenAIEngine

# Motor universal compatível com OpenAI para endpoints customizados ou locais
local_engine = OpenAIEngine(
    base_url="http://localhost:11434/v1",
    provider="ollama",
    api_key="ollama",
)

local_agent = Agent(
    name="LocalBot",
    instructions="You run locally via Ollama.",
    model="llama3.2:latest",
    engine=local_engine,
)
```

## 4. Ferramentas Determinísticas (`Tool` e `@tool`)

Ferramentas conferem poder de execução determinística aos agentes. Quando decoradas com `@tool`, o `chatflow-agent` constrói o schema de parâmetros a partir das anotações de tipo e dos valores padrão do Python. A descrição da ferramenta é o argumento `description=` ou, quando nenhuma descrição é fornecida, a docstring da função; seções da docstring como `Args:` não são analisadas como descrições por parâmetro:

```python
# [min-version: 0.3.0]
# [executable]
from chatflow_agent import tool

@tool(name="fetch_user_profile", description="Fetch user metadata from internal database.")
def fetch_user_profile(user_id: str) -> dict[str, str]:
    """Retrieve user details."""
    return {"user_id": user_id, "tier": "enterprise", "status": "active"}
```

Funções de ferramentas síncronas (`def`) e assíncronas (`async def`) são nativamente suportadas. Alternativamente, você pode utilizar o decorador `@agent.tool` diretamente em uma instância de agente.

## 5. Memória Resiliente e Concorrência (`SessionStore`)

O `chatflow-agent` trata persistência de estado e segurança de concorrência como cidadãos de primeira classe:

```python
from chatflow_agent import SQLiteSessionStore

# Armazenamento persistente de sessões em SQLite. default_max_turns é uma janela
# deslizante de histórico: mantém os últimos 40 turnos completos de cada sessão.
store = SQLiteSessionStore(
    db_path="./chat_sessions.db",
    default_max_turns=40,
)
```

### A Garantia de Reversão Transacional (_Rollback_)

Antes de processar um turno, a versão estável v0.3.4 registra o tamanho atual do histórico. Se uma exceção comum escapar do turno, o `Runner` trunca `session.history` até esse tamanho. Ele não restaura `active_agent` nem os metadados, e o cancelamento por `asyncio.wait_for` não é coberto por essa garantia.

### Proteção de Loop de Eventos e Bloqueio de Concorrência

- **Bloqueio de Sessão na v0.3.4:** Turnos que compartilham o mesmo `SessionContext` em memória são serializados por um `asyncio.Lock`; chamadas externas concorrentes aguardam e não geram `ReentrantTurnError`. Essa é uma garantia do loop de eventos, não de segurança entre threads ou processos.
- <VersionBadge version="0.4.0rc1" status="prerelease" /> **Proteções da Prévia:** O I/O de SQLite
  em arquivo é descarregado por `_run_blocking`, e `ReentrantTurnError` rejeita um turno aninhado da
  mesma sessão iniciado por código que já executa dentro desse turno. Chamadas externas
  independentes continuam aguardando na fila.

## 6. Transferências Multiagente (_Handoffs_)

Enxames multiagente delegam tarefas dinamicamente através de handoffs declarativos. Quando um agente declara um parceiro em `handoffs=[...]`, o `chatflow-agent` sintetiza uma ferramenta de transferência nomeada a partir do `name` do parceiro, em minúsculas e sanitizado: um parceiro chamado `BillingAgent` torna-se `transfer_to_billingagent`:

```python
from chatflow_agent import Agent, Runner

# Agente Especialista
billing_agent = Agent(
    name="BillingAgent",
    instructions="You specialize in invoices, receipts, and refund requests.",
    model="gpt-4o",
    provider="openai",
)

# Agente de Triagem Frontline
triage_agent = Agent(
    name="TriageAgent",
    instructions="Greet users. Transfer billing issues to BillingAgent.",
    model="gpt-4o",
    provider="openai",
    handoffs=[billing_agent],
)

runner = Runner(starting_agent=triage_agent)

# Executar turno com handoff
response = runner.run(
    session_id="user_billing_query",
    user_message="I need a copy of my invoice from last month.",
)

print(f"Responding agent: {response.active_agent_name}")
print(f"Message content: {response.content}")
```

O agente final que respondeu está acessível via `response.active_agent_name`. As transferências dentro de um turno são limitadas por `Runner(max_handoffs_per_turn=5)`; não existe uma detecção de ciclos separada.
