O `WhatsAppChannel` conecta enxames multiagente diretamente à API oficial da Meta WhatsApp Business Cloud. Projetado para ambientes de produção corporativos, ele inclui um servidor ASGI FastAPI embutido, webhooks verificados criptograficamente, deduplicação de mensagens, controle da janela de atendimento ao cliente e mascaramento de privacidade para números de telefone.

## Instalação

Instale o `chatflow-agent` com o extra `whatsapp` (`fastapi>=0.110.0`, `uvicorn>=0.29.0`):

```bash
pip install "chatflow-agent[whatsapp]"
```

## Arquitetura e Fluxo de Mensagens

```
Meta WhatsApp Cloud API
         |
         |  POST /webhook (JSON Assinado + X-Hub-Signature-256)
         v
+-------------------------------------------------------------------+
|                         WhatsAppChannel                           |
|  1. Verificação de Assinatura HMAC SHA-256 (app_secret)           |
|  2. Deduplicação por Message-ID (session store, at-most-once)     |
|  3. Mascaramento de Números nos Logs do SDK (_mask_phone)         |
|  4. Confirmação Imediata com HTTP 200                             |
+---------------------------------+---------------------------------+
                                  |
                         dispatch_async()
                                  |
                                  v
+---------------------------------+---------------------------------+
|                       chatflow-agent Runner                       |
|   - Bloqueio por Sessão (serializa só com SessionStore em memória)|
|   - Execução de Turno Multiagente (llm_timeout_seconds=30)        |
|   - Chamada de Ferramentas e Persistência de Estado               |
+---------------------------------+---------------------------------+
                                  |
                                  v
+---------------------------------+---------------------------------+
|                        Resposta de Saída                          |
|   - Verificação da Janela de Atendimento de 24h                   |
|   - Hook de Retorno on_24h_window_expired                         |
|   - Fragmentação de Mensagens (split_message)                     |
|   - POST https://graph.facebook.com/v21.0/{phone_number_id}       |
+-------------------------------------------------------------------+
```

## Configuração Rápida de Webhooks

<Steps>
  <Step>
    ### Coletar Credenciais da Meta Cloud API

    No seu [Painel de Desenvolvedores da Meta](https://developers.facebook.com/):
    1. **Verify Token:** Um token secreto personalizado que você define para a verificação inicial do webhook.
    2. **Access Token:** Token de acesso permanente de usuário do sistema com permissões de `whatsapp_business_messaging`.
    3. **Phone Number ID:** O ID do seu número de teste ou produção registrado no WhatsApp Business.
    4. **App Secret:** O Segredo do Aplicativo da Meta em Configurações do app &gt; Básico (utilizado para validação de assinatura HMAC).
  </Step>

  <Step>
    ### Inicializar e Vincular o Canal

```python
import os
from chatflow_agent import Agent, Runner
from chatflow_agent.channels import WhatsAppChannel
from chatflow_agent.core.memory import SQLiteSessionStore

# Definir seu agente
customer_service = Agent(
    name="CustomerService",
    instructions="Provide courteous, professional customer support.",
)

store = SQLiteSessionStore("whatsapp_sessions.db", dedup_ttl_hours=192)
runner = Runner(starting_agent=customer_service, session_store=store)

# Inicializar canal do WhatsApp. Leia todas as credenciais do ambiente sem
# valor de fallback: uma variável ausente falha na inicialização em vez de
# executar com um segredo publicamente conhecido.
whatsapp = WhatsAppChannel(
    verify_token=os.environ["WHATSAPP_VERIFY_TOKEN"],
    access_token=os.environ["WHATSAPP_ACCESS_TOKEN"],
    phone_number_id=os.environ["WHATSAPP_PHONE_NUMBER_ID"],
    app_secret=os.environ["WHATSAPP_APP_SECRET"],
    verify_signature=True,
)

whatsapp.attach(runner)

if __name__ == "__main__":
    # Inicia o servidor ASGI FastAPI na porta 8000
    whatsapp.run(host="0.0.0.0", port=8000)
```
  </Step>

  <Step>
    ### Configurar a URL do Webhook no Painel da Meta

    Aponte a URL de Webhook da Meta para `https://seu-dominio.com/webhook` e defina o Verify Token correspondente. A Meta enviará uma requisição `GET` para validar a assinatura, a qual o `WhatsAppChannel` responderá imediatamente.
  </Step>
</Steps>

## Padrões de Segurança e Verificação

### Validação Criptográfica de Assinaturas HMAC SHA-256

A Meta assina toda carga útil recebida via POST utilizando seu App Secret e envia a assinatura no cabeçalho `X-Hub-Signature-256`.

<Callout type="warn" title="Política de Assinatura Fail-Closed">
Se `verify_signature=True` (o padrão), omitir `app_secret` gera `ValueError` ao construir o canal. Depois da construção, um cabeçalho `X-Hub-Signature-256` ausente, malformado ou inválido é rejeitado com `HTTP 403 Forbidden`. Nunca desative a verificação de assinatura em implantações públicas de produção.
</Callout>

### Validação de Requisições e Códigos de Status HTTP

Antes de qualquer turno ser executado, o endpoint `POST /webhook` aplica estas verificações:

| Condição | Resposta |
| :--- | :--- |
| Cabeçalho `Content-Length` ausente | `411 Length Required` |
| Valor de `Content-Length` inválido, ou um corpo que não é JSON válido | `400 Bad Request` |
| `Content-Length` ou corpo maior que `max_body_size` (padrão 1 MB) | `413` |
| `X-Hub-Signature-256` ausente, malformado ou inválido (com `verify_signature=True`) | `403 Forbidden` |
| Requisição válida, incluindo entregas duplicadas | `200 OK` |

O `GET /webhook` responde ao desafio de inscrição da Meta com uma comparação do verify token em tempo constante, e o `GET /health` retorna um status de saúde. As rotas de documentação do FastAPI (`/docs`, `/redoc`, `/openapi.json`) ficam desativadas, a menos que você passe `enable_docs=True`.

As requisições devem trazer um cabeçalho `Content-Length`; verifique se nenhum proxy à frente do servidor reenvia o corpo com codificação de transferência em blocos (*chunked*).

### Proteção de Dados Pessoais (PII) e Mascaramento de Números

O `WhatsAppChannel` mascara números de telefone nas mensagens de log do próprio SDK, mantendo os quatro primeiros e os três últimos caracteres. A Meta envia o número do remetente apenas com dígitos:

```python
# Telefone de entrada sem formatação: "14155552671"
# Saída registrada nos logs:         "1415***671"
```

O mascaramento se aplica apenas a essas linhas de log. O número sem mascaramento ainda aparece:

* no corpo da resposta JSON do webhook (campo `"sender"`);
* no ID da sessão e nos metadados do turno (`"phone"`) e, portanto, no session store;
* no argumento passado para `on_24h_window_expired`;
* nas respostas de erro da Meta, que são registradas nos logs como recebidas.

Trate os logs, o banco de dados de sessões e quaisquer logs de acesso HTTP como dados pessoais.

## Concorrência, Prazos e Tempos Limite

A versão estável v0.3.4 expõe o seguinte prazo para a avaliação do modelo:

| Parâmetro | Padrão | Finalidade |
| :--- | :--- | :--- |
| `llm_timeout_seconds` | `30.0` | Prazo aplicado pelo `WhatsAppChannel` enquanto aguarda o turno do runner. |

`queue_timeout_seconds` e o padrão de `120.0` segundos são recursos da prerelease v0.4.0rc1. `max_concurrent_tasks` não é parâmetro do construtor na v0.3.4 nem na v0.4.0rc1. Na v0.3.4, turnos da mesma sessão aguardam o lock sem prazo de fila. Um timeout cancela a espera e retorna a `fallback_message`, mas a v0.3.4 não garante rollback em caso de cancelamento.

## Rastreamento da Janela de Atendimento ao Cliente de 24 Horas

A Meta restringe estritamente o envio de mensagens em formato livre para o período de **24 horas contadas a partir da última mensagem enviada pelo usuário**. Tentar enviar texto livre fora dessa janela gera o código de erro `131047` da API da Meta.

O `WhatsAppChannel` inclui um hook de callback dedicado `on_24h_window_expired`. Ele é chamado com um único argumento, o número de telefone do destinatário (sem mascaramento). Na v0.3.4, ele deve ser uma função `async def` ou uma função comum; outros callables que retornam uma corrotina (como um objeto com `async __call__`) não são aguardados. Exceções levantadas pelo hook são registradas nos logs e não interrompem o canal:

```python
async def handle_expired_window(phone_number: str) -> None:
    """Triggered when a reply cannot be delivered as a free-form message."""
    print(f"24h window closed for {phone_number}. Queuing template notification...")
    # Acionar mensagem de modelo (Template) aprovada no WhatsApp, ticket de CRM ou fallback por e-mail
 
whatsapp = WhatsAppChannel(
    verify_token="token",
    access_token="token",
    phone_number_id="id",
    app_secret="secret",
    on_24h_window_expired=handle_expired_window,
)
```

## Deduplicação de Mensagens (TTL)

Os webhooks da Meta frequentemente realizam reenvios duplicados se a latência de rede atrasar a confirmação. O `WhatsAppChannel` registra o ID de cada mensagem no session store vinculado (`SessionStore` ou `SQLiteSessionStore`) antes de enfileirar o turno. O TTL é o `dedup_ttl_hours` do store (padrão de 192 horas, 8 dias), por exemplo `SQLiteSessionStore(..., dedup_ttl_hours=192)`. Cargas úteis de webhooks duplicadas recebem respostas imediatas com `HTTP 200` sem reexecutar turnos de agentes.

<Callout type="warn" title="Entrega no máximo uma vez (at-most-once)">
O ID da mensagem é registrado <em>antes</em> de o turno em segundo plano ser executado. Se o processo falhar ou reiniciar enquanto esse turno está em execução, a mensagem é perdida: as novas tentativas da Meta para ela são então descartadas como duplicatas.
</Callout>

O `WhatsAppChannel` também aceita um argumento `dedup_ttl_hours` na v0.3.4, mas ele é armazenado e nunca utilizado: apenas a configuração do session store se aplica.

Para cargas úteis no formato genérico (não Meta) sem ID de mensagem, a v0.3.4 deriva o ID a partir do `hash()` da carga útil. Mensagens genéricas idênticas do mesmo remetente são, portanto, tratadas como duplicatas durante todo o TTL, e o ID derivado muda entre reinicializações do processo.
