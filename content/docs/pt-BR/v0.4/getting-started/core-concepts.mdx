O `chatflow-agent` é construído sobre seis primitivas arquiteturais fundamentais que, combinadas, viabilizam sistemas conversacionais de IA leves, modulares e tolerantes a falhas:

## O que é um chatflow?

No `chatflow-agent`, chamamos de **chatflow** o percurso que uma conversa desenvolve enquanto os agentes processam mensagens, usam ferramentas e transferem tarefas para outros agentes. O `Runner` coordena cada turno, carrega e preserva o estado da sessão e invoca o agente ativo. Os agentes interpretam a solicitação atual e decidem se respondem, usam uma ferramenta ou transferem a conversa; as ferramentas executam as operações determinísticas definidas pela aplicação.

O percurso se desenvolve de acordo com as solicitações do usuário e o [estado persistente da sessão](/pt-BR/docs/v0.4/guides/sessions-state), sem exigir uma sequência fixa. Os guias de [ferramentas](/pt-BR/docs/v0.4/guides/tools) e [handoffs](/pt-BR/docs/v0.4/guides/multi-agent-handoffs) explicam esses recursos em detalhes. As integrações de canais, como [Telegram](/pt-BR/docs/v0.4/integrations/telegram), [WhatsApp](/pt-BR/docs/v0.4/integrations/whatsapp) e [webhooks](/pt-BR/docs/v0.4/integrations/webhook), transportam mensagens entre plataformas externas e o runner.

**Exemplo conceitual:** Uma aplicação construída com a biblioteca poderia permitir que um usuário solicitasse um agendamento. Um agente identifica a especialidade, outro consulta a disponibilidade por meio de uma ferramenta definida pela aplicação e a aplicação registra o agendamento depois que o usuário o confirma. O sistema de agendamento e suas ferramentas de negócio pertencem à aplicação; eles não são recursos integrados do `chatflow-agent`.

## 1. O Agente (`Agent`)

Um `Agent` representa um ator autônomo com persona explícita, instruções em prompt de sistema, um modelo e motor de LLM designados e acesso a ferramentas ou agentes de transferência (_handoffs_).

```python
# [min-version: 0.3.0]
# [executable]
from chatflow_agent import Agent

# Instruções de prompt estáticas com modelo alvo
agent = Agent(
    name="TriageBot",
    instructions="You are the front desk concierge. Route questions to specialists.",
    model="gpt-4o",
)
```

### Instruções Dinâmicas

As instruções podem ser uma string estática ou um invocável (_callable_) em Python (`Callable[[], str]`). Instruções dinâmicas são avaliadas no início de cada turno:

```python
# [min-version: 0.3.0]
# [executable]
from datetime import datetime
from chatflow_agent import Agent

def get_live_instructions() -> str:
    now = datetime.now().strftime("%Y-%m-%d %H:%M:%S")
    return f"You are a scheduling assistant. Current server time is {now}."

agent = Agent(
    name="ScheduleBot",
    instructions=get_live_instructions,
    model="gemini-2.5-flash",
)
```

  lançando um <code>ValueError</code> caso nomes duplicados sejam detectados para evitar colisões na

## 2. O Motor de Execução (`Runner`)

O `Runner` orquestra o ciclo de vida da conversação, gerenciando:

1. O carregamento do contexto da sessão e histórico de mensagens a partir do `SessionStore`.
2. A criação de um ponto de verificação (_checkpoint_) do histórico, do agente ativo e dos metadados da sessão antes de executar o turno.
3. A invocação do motor do modelo.
4. O parsing de chamadas a ferramentas, a execução das funções correspondentes e o envio dos resultados de volta ao modelo até a obtenção de uma resposta textual final.
5. A manutenção das alterações em caso de sucesso, ou a restauração do checkpoint se o turno lançar uma exceção, for cancelado ou atingir seu `turn_timeout`.

Invocação síncrona, para scripts e ferramentas de CLI (sem um event loop em execução):

```python
from chatflow_agent import Agent, Runner, SessionStore

agent = Agent(
    name="Assistant",
    instructions="Concise scheduling assistant.",
    model="gpt-4o",
)

store = SessionStore()

runner = Runner(
    starting_agent=agent,
    session_store=store,
)

response = runner.run(
    session_id="user_123",
    user_message="Book a meeting tomorrow at 3 PM",
)
```

Invocação assíncrona, dentro de um event loop (servidores web, bots, aplicações `asyncio`):

```python
# [min-version: 0.4.0rc1]
# [no-exec: requires real openai api key for live response]
import asyncio

from chatflow_agent import Agent, Runner

async def main() -> None:
    agent = Agent(
        name="Assistant",
        instructions="Concise scheduling assistant.",
        model="gpt-4o",
    )
    async with Runner(starting_agent=agent) as runner:
        response = await runner.run_async(
            session_id="user_123",
            user_message="Book a meeting tomorrow at 3 PM",
        )
        print(response.content)

asyncio.run(main())
```

<Callout type="info" title="turn_timeout em v0.4.0rc1">
  Na versão <VersionBadge version="0.4.0rc1" status="prerelease" />, <code>Runner.run_async</code>{' '}
  introduz o parâmetro opcional nomeado <code>turn_timeout: float | None = None</code> (por exemplo,{' '}
  <code>turn_timeout=30.0</code>). Se um turno exceder o prazo limite, ele é cancelado e o estado é
  revertido atomicamente.
</Callout>

## 3. Motores de Provedores (`Engines`)

Toda a comunicação com modelos no `chatflow-agent` é desacoplada sob a interface `BaseEngine`. Os motores comunicam-se através de REST HTTP assíncrono via `httpx`, eliminando a necessidade de bibliotecas cliente monolíticas de fornecedores:

- **`OpenAIEngine`**: Suporta modelos OpenAI e qualquer API compatível com OpenAI (Groq, DeepSeek, xAI Grok, Ollama, vLLM) através de `base_url`.
- **`AnthropicEngine`**: Integração REST direta com modelos Claude da Anthropic.
- **`GeminiEngine`**: Integração com Google Gemini. Na versão <VersionBadge version="0.4.0rc1" status="prerelease" />, foi totalmente reescrito com chamadas REST nativas.

```python
from chatflow_agent import Agent, OpenAIEngine

# Motor universal compatível com OpenAI para endpoints customizados ou locais
local_engine = OpenAIEngine(
    base_url="http://localhost:11434/v1",
    provider="ollama",
    api_key="ollama",
)

local_agent = Agent(
    name="LocalBot",
    instructions="You run locally via Ollama.",
    model="llama3.2:latest",
    engine=local_engine,
)
```

## 4. Ferramentas Determinísticas (`Tool` e `@tool`)

As ferramentas conferem aos agentes poder de execução determinístico. Quando decoradas com `@tool`, o `chatflow-agent` constrói o schema de parâmetros a partir das anotações de tipo do Python e dos valores padrão. A descrição da ferramenta é o argumento `description=`, ou a docstring da função quando nenhuma descrição é informada; seções da docstring como `Args:` não são interpretadas como descrições por parâmetro:

```python
# [min-version: 0.3.0]
# [executable]
from chatflow_agent import tool

@tool(name="fetch_user_profile", description="Fetch user metadata from internal database.")
def fetch_user_profile(user_id: str) -> dict[str, str]:
    """Retrieve user details."""
    return {"user_id": user_id, "tier": "enterprise", "status": "active"}
```

Funções síncronas (`def`) e assíncronas (`async def`) são suportadas nativamente. Alternativamente, você pode usar o decorador `@agent.tool` diretamente em uma instância de agente.

## 5. Memória Resiliente e Concorrência (`SessionStore`)

O `chatflow-agent` trata a persistência de estado e a segurança de concorrência como prioridades de primeira classe:

```python
from chatflow_agent import SQLiteSessionStore

# Armazenamento persistente de sessões em SQLite. default_max_turns é uma janela
# deslizante de histórico: mantém os últimos 40 turnos completos de cada sessão.
store = SQLiteSessionStore(
    db_path="./chat_sessions.db",
    default_max_turns=40,
)
```

### A Garantia de Reversão Transacional (_Rollback_)

Antes de processar um turno, o `Runner` cria um checkpoint do histórico, do agente ativo e dos metadados da sessão. Se uma exceção escapar do turno (por exemplo, uma indisponibilidade do provedor), o turno for cancelado ou o `turn_timeout` expirar, o checkpoint é restaurado antes que o erro seja lançado. Assim, turnos corrompidos ou parciais nunca degradam o histórico da conversação.

### Proteção do Event Loop e Escudos de Concorrência

- **Descarga para Pools de Threads:** A E/S de SQLite baseado em arquivo roda nas threads trabalhadoras dedicadas do próprio store, impedindo que bloqueios de sistema de arquivos travem o loop de eventos asyncio do Python. Stores `":memory:"` permanecem no event loop.
- **Bloqueio de Sessão:** Os turnos de uma mesma sessão são serializados (por store e por event loop, tanto para `SessionStore` quanto para `SQLiteSessionStore`); requisições simultâneas para uma sessão aguardam o bloqueio.
- **Proteção contra Reentrância (`ReentrantTurnError`):** Iniciar um turno para uma sessão a partir de código iniciado pelo turno em execução dessa mesma sessão (uma ferramenta, ou uma task ou thread criada por ela) lança `ReentrantTurnError` em vez de causar um deadlock. Use `Runner.spawn_turn()` para enfileirar um turno de acompanhamento.

## 6. Handoffs Multiagente (`Handoffs`)

Enxames multiagente delegam tarefas dinamicamente através de transferências declarativas (_handoffs_). Quando um agente declara um par em `handoffs=[...]`, o `chatflow-agent` sintetiza uma ferramenta de transferência nomeada a partir do `name` do par, transliterado para ASCII, convertido para minúsculas e sanitizado: um par chamado `BillingAgent` se torna `transfer_to_billingagent`:

```python
from chatflow_agent import Agent, Runner

# Agente Especialista
billing_agent = Agent(
    name="BillingAgent",
    instructions="You specialize in invoices, receipts, and refund requests.",
    model="gpt-4o",
)

# Agente de Triagem Inicial
triage_agent = Agent(
    name="TriageAgent",
    instructions="Greet users. Transfer billing issues to BillingAgent.",
    model="gpt-4o",
    handoffs=[billing_agent],
)

runner = Runner(starting_agent=triage_agent)

# Executar turno com transferência
response = runner.run(
    session_id="user_billing_query",
    user_message="I need a copy of my invoice from last month.",
)

print(f"Responding agent: {response.active_agent_name}")
print(f"Message content: {response.content}")
```

O agente que gerou a resposta final fica visível através de `response.active_agent_name`. As transferências dentro de um turno são limitadas por `Runner(max_handoffs_per_turn=5)`; não existe uma detecção de ciclos separada.
