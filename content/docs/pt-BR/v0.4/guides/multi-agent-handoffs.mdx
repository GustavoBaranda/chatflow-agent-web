A coordenação multiagente no **chatflow-agent** é modelada em torno de **enxames autônomos ponto a ponto (peer-to-peer swarms)**. Em vez de depender de um coordenador centralizado ou de grafos rígidos codificados manualmente, os agentes delegam tarefas a pares especializados de forma autônoma invocando ferramentas sintetizadas de transferência (*handoff*).

Quando um agente dispara uma transferência, o contexto da conversa é preservado de forma transparente, o ponteiro de agente ativo é atualizado e o novo agente continua o turno imediatamente dentro do mesmo ciclo de execução.

---

## O Modelo Mental de Enxame

Em uma arquitetura de enxame, cada agente especializa-se em um domínio específico (ex.: triagem, faturamento, suporte técnico, reembolsos). A coordenação acontece de forma orgânica através do diálogo:

1. **Delegação Descentralizada:** Agentes sabem para quais parceiros podem transferir o atendimento através da sua lista `handoffs`.
2. **Tomada de Decisão Dinâmica:** O LLM decide em tempo de execução se responde diretamente, aciona uma ferramenta de domínio ou transfere o controle para um parceiro.
3. **Execução Transparente:** O usuário final interage com um endpoint conversacional unificado (`Runner`), sem necessidade de gerenciar múltiplos modelos ou agentes colaborando nos bastidores.

## Declarando Handoffs entre Agentes

As relações de transferência podem ser declaradas durante a instanciação ou de forma imperativa:

### Método 1: Declaração no Construtor
Passe uma lista de instâncias alvo de `Agent` no parâmetro `handoffs`:

```python
# [min-version: 0.3.0]
# [executable]
from chatflow_agent import Agent

# Definir primeiro os agentes de destino especializados
billing_agent = Agent(
    name="BillingSpecialist",
    instructions="Handle payments, invoice queries, and subscription upgrades.",
    model="gemini-2.5-flash",
)

technical_agent = Agent(
    name="TechnicalSupport",
    instructions="Diagnose software bugs, API errors, and configuration issues.",
    model="gemini-2.5-flash",
)

# O agente de triagem roteia para os especialistas
triage_agent = Agent(
    name="TriageAgent",
    instructions=(
        "Welcome the user and determine their needs. "
        "Transfer billing questions to BillingSpecialist and technical questions to TechnicalSupport."
    ),
    handoffs=[billing_agent, technical_agent],
    model="gemini-2.5-flash",
)
```

### Método 2: Handoffs Bidirecionais e Cíclicos
Especialistas frequentemente precisam transferir usuários de volta para a triagem. Use `agent.add_handoff()` para estabelecer vínculos bidirecionais:

```python
# [min-version: 0.3.0]
# [executable]
from chatflow_agent import Agent

support = Agent(name="Support", instructions="General support", model="gpt-4o")
billing = Agent(name="Billing", instructions="Billing support", model="gpt-4o")

# Estabelecer transferência bidirecional
support.add_handoff(billing)
billing.add_handoff(support)

assert any(h.name == "Billing" for h in support.handoffs)
assert any(h.name == "Support" for h in billing.handoffs)
```

<Callout type="warn" title="Proibição de Transferência para Si Mesmo">
Um agente não pode registrar uma transferência para si mesmo. Invocar <code>agent.add_handoff(agent)</code> lança imediatamente um <code>ValueError("Agent 'X' cannot register a handoff to itself.")</code>.
</Callout>

## Ferramentas Sintéticas de Roteamento sob o Capô

Quando um agente define parceiros em `handoffs`, o `chatflow-agent` sintetiza automaticamente ferramentas de roteamento dedicadas, expostas através de `agent.get_all_tools()`.

Para cada agente parceiro:
* **Nome da Ferramenta:** Gerado como `transfer_to_<sanitized_name>` (ex.: `transfer_to_billingspecialist`).
* **Descrição da Ferramenta:** Combina o nome do agente alvo com um trecho de suas instruções:
  `"Hand off the dialogue to 'BillingSpecialist'. Target agent specialty: Handle payments, invoice queries..."`
* **Assinatura:** Aceita um parâmetro opcional `reason: str | None = None`.
* **Retorno:** Retorna uma carga útil tipada `Handoff(target_agent_name="BillingSpecialist", reason=...)`.

Como as ferramentas de transferência se comportam exatamente como chamadas de função comuns, o modelo aprende naturalmente quando transferir o controle com base na intenção do usuário e nas descrições das ferramentas.

## Ciclo de Vida da Execução do Handoff no `Runner`

Quando `runner.run_async()` processa um turno:

```
[Mensagem do Usuário] 
       │
       ▼
 [Agente Ativo] ──(Gera Chamada de Ferramenta)──► transfer_to_billingspecialist(reason="...")
                                                            │
                                                            ▼
                                                   [Executa Handoff]
                                                            │
                                                            ▼
                                                  [Troca Agente Ativo]
                                               (session.set_active_agent)
                                                            │
                                                            ▼
                                                [Próxima Geração do Modelo]
                                                (BillingSpecialist responde)
                                                            │
                                                            ▼
                                                    [Resposta Final]
```

1. **Invocação da Ferramenta:** O LLM emite uma chamada de ferramenta para `transfer_to_billingspecialist`.
2. **Verificação de Autorização:** Na v0.4.0rc1, o destino deve estar declarado nos `handoffs` do **agente atual**; estar registrado no `Runner` não é suficiente. Caso contrário, é lançado um `AgentHandoffError` (`"Agent 'X' is not authorized to hand off to 'Y'."`). Pares adicionados com `add_handoff()` depois da criação do `Runner` são registrados automaticamente quando usados pela primeira vez.
3. **Atualização do Agente Ativo:** O `Runner` atualiza `session.set_active_agent(target_agent)`.
4. **Injeção do Resultado do Handoff:** Um `ToolResult` contendo `status: "HANDOFF_SUCCESS"` e o motivo da transferência é adicionado ao histórico da sessão.
5. **Continuação Imediata do Turno:** Dentro da mesma chamada `runner.run()`, o novo agente ativo é acionado com o histórico atualizado para formular sua resposta.

## Prevenção de Ciclos e Limites de Turno

Transferências descontroladas entre agentes poderiam disparar loops infinitos se os prompts fossem ambíguos. O `chatflow-agent` protege sua execução com salvaguardas nativas:

* **`max_handoffs_per_turn` (Padrão: 5):**
  O número máximo de transferências de agentes permitidas dentro de um único turno de mensagem do usuário. Na v0.4.0rc1, o limite é verificado antes da troca de agente: a transferência que o excederia não é aplicada, sua chamada recebe o resultado de erro `"Maximum agent transfers exceeded for a single turn."` e cada chamada restante daquela mensagem do modelo recebe um resultado "Tool skipped".
* **`max_tool_iterations` (Padrão: 10):**
  O número máximo de rodadas modelo/ferramenta por turno. Uma rodada é uma geração do modelo mais todas as chamadas de ferramenta que ela solicitou, portanto uma rodada pode executar várias ferramentas. Quando o limite é atingido, o turno termina com uma resposta de fallback "Execution iteration limit reached".

```python
from chatflow_agent import Agent, Runner

triage = Agent(name="Triage", instructions="...", model="gpt-4o")

# Configurar limites de turno mais estritos para endpoints de alta demanda ou custo controlado
runner = Runner(
    starting_agent=triage,
    max_handoffs_per_turn=3,
    max_tool_iterations=6,
)
```

## Diferenças entre Versões e Recursos de Pré-lançamento

A geração e sanitização de handoffs trazem melhorias substanciais de confiabilidade nas versões mais recentes:

### Versão Estável (`v0.3.4`)
* <VersionBadge version="0.3.4" status="stable" /> Sanitização básica por regex: `clean = re.sub(r"[^a-zA-Z0-9_]", "_", name.strip().lower())`.
* Histórico de sessão compartilhado preserva todo o contexto conversacional entre transferências.

### Melhorias de Pré-lançamento (`v0.4.0rc1`)
* <VersionBadge version="0.4.0rc1" status="prerelease" /> **Transliteração Unicode NFKD:** Converte automaticamente caracteres com acento para ASCII limpo (ex.: `AtenciónAlCliente` torna-se `transfer_to_atencionalcliente`).
* <VersionBadge version="0.4.0rc1" status="prerelease" /> **Fallback Determinístico por Hash:** Nomes de agentes em alfabetos não latinos (ex.: japonês, árabe, cirílico) ou emojis recorrem a um prefixo hash SHA-256 determinístico (`transfer_to_u<hash>`) garantindo sintaxe válida de identificador.
* <VersionBadge version="0.4.0rc1" status="prerelease" /> **Desambiguação em Colisões:** Se dois agentes gerarem nomes sanitizados equivalentes, sufixos numéricos (`_2`, `_3`) são adicionados automaticamente para evitar sobreposição de esquemas.
* <VersionBadge version="0.4.0rc1" status="prerelease" /> **Limite de Comprimento:** Identificadores de ferramentas de handoff são limitados a 60 caracteres para respeitar as restrições dos provedores.
* <VersionBadge version="0.4.0rc1" status="prerelease" /> **Encaminhamento de Atualizações de Contexto:** `session.set_active_agent(agent, context_updates)` armazena `Handoff.context_updates` nos metadados da sessão quando o handoff acontece. As ferramentas embutidas `transfer_to_*` nunca preenchem `context_updates`; somente uma ferramenta customizada que retorne seu próprio `Handoff` pode fazê-lo.
* <VersionBadge version="0.4.0rc1" status="prerelease" /> **Nomes de Agentes Únicos (mudança incompatível):** Construir um `Runner` cujo grafo de handoffs contenha duas instâncias distintas de `Agent` com o mesmo `name` lança `ValueError` (`"Duplicate agent name 'Billing': distinct Agent instances cannot share a name in one Runner tree."`). A mesma verificação se aplica a pares adicionados posteriormente com `add_handoff()`. Na v0.3.4, a segunda instância era ignorada silenciosamente. Nomes vazios ou compostos apenas por espaços em branco lançam `ValueError` quando o `Agent` é criado.

## Exemplo Completo: Enxame de Suporte Multi-Nível

```python
from chatflow_agent import Agent, Runner, tool
from chatflow_agent.core.memory import SessionStore

# 1. Ferramentas especializadas
@tool
def issue_refund(transaction_id: str, amount: float) -> dict:
    """Process a refund back to customer original payment method."""
    return {"status": "REFUNDED", "transaction_id": transaction_id, "amount": amount}

@tool
def lookup_kb_article(topic: str) -> str:
    """Search knowledge base for troubleshooting steps."""
    return f"Knowledge base instructions for {topic}: Clear cache and restart application."

# 2. Agentes de destino especializados
billing_agent = Agent(
    name="BillingAgent",
    instructions="Assist with refunds and payment disputes. Use issue_refund when appropriate.",
    tools=[issue_refund],
    model="gemini-2.5-flash",
)

tech_agent = Agent(
    name="TechSupportAgent",
    instructions="Assist with software errors. Use lookup_kb_article for troubleshooting.",
    tools=[lookup_kb_article],
    model="gemini-2.5-flash",
)

# 3. Agente de triagem
triage_agent = Agent(
    name="TriageAgent",
    instructions=(
        "Welcome the user. Ask what they need help with. "
        "Transfer billing/refund issues to BillingAgent and technical bugs to TechSupportAgent."
    ),
    handoffs=[billing_agent, tech_agent],
    model="gemini-2.5-flash",
)

# 4. Permitir que os especialistas transfiram de volta para a triagem se necessário
billing_agent.add_handoff(triage_agent)
tech_agent.add_handoff(triage_agent)

# 5. Inicializar o runner
store = SessionStore()
runner = Runner(starting_agent=triage_agent, session_store=store)

# 6. Executar diálogo
response = runner.run(
    session_id="customer-session-101",
    user_message="I have an unexpected charge on my invoice and need a refund.",
)

print("Active Agent:", response.active_agent_name)
print("Response:", response.content)
print("Handoff:", response.handoff)
```

## Armadilhas Comuns e Boas Práticas

### 1. Destinos de Handoff Devem Ser Declarados no Agente Atual
O `Runner` indexa automaticamente todos os agentes alcançáveis através da árvore de handoffs do `starting_agent`. Na v0.4.0rc1, registrar um agente com `runner.register_agent(...)` **não** o torna um destino de handoff: um agente só pode transferir para os pares em seus próprios `handoffs`. Para adicionar um destino dinamicamente, declare-o no agente que fará a transferência; o `Runner` o registra no primeiro uso:
```python
# Tornar specialist_agent alcançável a partir de triage_agent em tempo de execução:
triage_agent.add_handoff(specialist_agent)
```

### 2. Instruções de Handoff Excessivamente Genéricas
Certifique-se de que as instruções do agente de destino indiquem com precisão os tópicos que ele soluciona. Se dois agentes possuírem descrições sobrepostas, os modelos podem hesitar ou transferir de forma imprevisível.

### 3. Preservando a Identidade da Sessão
Nunca crie um novo `session_id` quando esperar que um handoff continue o diálogo. O estado do handoff e a transição do agente são registrados dentro da sessão ativa.
