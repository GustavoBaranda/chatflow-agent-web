Agentes de IA autônomos capazes de invocar ferramentas, consultar bancos de dados internos e se comunicar através de canais externos apresentam desafios únicos de segurança. A estratégia de defesa em profundidade exige blindar a fronteira do LLM, proteger credenciais contra exfiltração e impor autorização estrita em webhooks de canais.

O `chatflow-agent` incorpora mecanismos de defesa diretamente em seus motores centrais, runners e implementações de canal.

## Arquitetura de Segurança Central

```text
Untrusted Input (Webhooks / Chat Channels)
          │
          ▼
1. Inbound Authentication (WhatsApp HMAC SHA-256 / Verify Token / Telegram Admin Check)
          │
          ▼
2. Session Concurrency & Reentrancy Guards (Session Lock / ReentrantTurnError)
          │
          ▼
3. Agent Boundaries (Per-Agent Tool Scoping / Iteration and Handoff Limits)
          │
          ▼
4. Credential Isolation & Egress Guards (ValueError on Custom Host / No API Key Leak)
```

O SDK não isola as ferramentas em sandbox: elas rodam no processo da aplicação com todos os seus privilégios, e na v0.4.0rc1 os argumentos de ferramentas fornecidos pelo modelo são passados à função sem validação em tempo de execução. A autenticação de entrada para canais customizados, como tokens Bearer, é implementada pela sua aplicação.

## Proteção de Credenciais e Bloqueio de Exfiltração

Ao conectar-se a gateways de inferência privados ou proxies, é comum desenvolvedores sobrescreverem a `base_url`. Se um motor enviasse credenciais oficiais de nuvem (como a `OPENAI_API_KEY`) para um endpoint arbitrário de terceiros, tokens secretos poderiam vazar.

O `chatflow-agent` impõe uma proteção automática de credenciais no `OpenAIEngine`:

```python
from chatflow_agent.core.engines.openai_compatible import OpenAIEngine

# [SAFE] Endpoint oficial com variável de ambiente
official_engine = OpenAIEngine(provider="openai")

# [SAFE] Endpoint customizado com token interno explicitamente informado
internal_engine = OpenAIEngine(
    base_url="https://gateway.internal.corp/v1",
    api_key="internal-bearer-token",
)

# [SAFE] Inferência offline local: nenhuma chave é necessária. O motor usa
# OLLAMA_API_KEY se estiver definida; caso contrário, a chave provisória "ollama".
local_engine = OpenAIEngine(
    base_url="http://localhost:11434/v1",
    provider="ollama",
)
```

<Callout type="warn" title="Proteção Automática com ValueError">
Se você fornecer uma `base_url` remota customizada sem uma `api_key` explícita, o `OpenAIEngine` se recusa a reutilizar a `OPENAI_API_KEY` (ou qualquer outra chave de provedor) do ambiente e levanta um `ValueError`. Isso impede a exfiltração acidental de credenciais para proxies não confiáveis. Hosts de loopback (`localhost`, `127.0.0.1`, `::1`, `0.0.0.0`) são isentos e recebem uma chave provisória. Na v0.4.0rc1, o `GeminiEngine` também nunca segue redirecionamentos HTTP e remove a chave de API de suas mensagens de erro.
</Callout>

## Protocolos de Segurança em Canais

### Assinaturas HMAC SHA-256 no WhatsApp

A Meta entrega eventos de webhook do WhatsApp acompanhados do cabeçalho `X-Hub-Signature-256` calculado como `HMAC-SHA256(payload, app_secret)`.

O `WhatsAppChannel` valida toda carga útil recebida antes de processar o JSON ou despachar turnos:

```python
import os
from chatflow_agent.channels import WhatsAppChannel

# Sempre mantenha a verificação de assinatura ativada em produção
channel = WhatsAppChannel(
    verify_token=os.environ["WHATSAPP_VERIFY_TOKEN"],
    access_token=os.environ["WHATSAPP_ACCESS_TOKEN"],
    phone_number_id=os.environ["WHATSAPP_PHONE_NUMBER_ID"],
    app_secret=os.environ["WHATSAPP_APP_SECRET"],
    verify_signature=True,  # Assinaturas de requisição ausentes/inválidas recebem HTTP 403
)
```

Com `verify_signature=True` (o padrão), construir o canal sem um `app_secret` lança `ValueError`. Leia os segredos sem valores de fallback: um valor provisório não vazio, como `"secret"`, passaria nessa verificação e permitiria que qualquer pessoa que o conhecesse forjasse requisições assinadas.

### Mascaramento Automático de Números de Telefone

Números de telefone de clientes recebidos via WhatsApp são Informações Pessoalmente Identificáveis (PII). O `WhatsAppChannel` mascara os valores em suas próprias mensagens de log mantendo os quatro primeiros e os três últimos caracteres da entrada; por exemplo, o remetente da Meta `14155552671` torna-se `1415***671`. O número original ainda aparece na resposta JSON do webhook (`"sender"`), no ID de sessão e nos metadados armazenados pelo armazenamento de sessões, no argumento passado para `on_24h_window_expired` e nas respostas de erro da Meta que são registradas no log tal como recebidas. Aplicações e ferramentas externas devem aplicar suas próprias políticas de redação.

### Administração de Chats em Grupo no Telegram

Em chats em grupo, múltiplos usuários interagem com o mesmo bot. Permitir que qualquer membro execute `/reset` poderia interromper o fluxo de trabalho de outros participantes.

O `TelegramChannel` impõe verificações de autorização no comando `/reset`: ele consulta `get_chat_member` e autoriza o reset apenas se o remetente possuir status de `creator` ou `administrator` no grupo.

## Injeção de Prompt e Fronteiras de Ferramentas

A injeção de prompt ocorre quando entradas de usuários não confiáveis manipulam o LLM para ignorar instruções do sistema ou invocar ferramentas não autorizadas.

Para mitigar riscos de injeção de prompt:

1. **Princípio do Menor Privilégio:** Conceda a cada agente especializado somente as ferramentas estritamente necessárias. Um `BillingAgent` não deve ter acesso a ferramentas de deleção de banco de dados ou reinicialização de servidores.
2. **Valide os Argumentos Dentro de Cada Ferramenta:** A v0.4.0rc1 não valida nem converte em tempo de execução os argumentos fornecidos pelo modelo; as anotações de tipo apenas moldam o esquema que o modelo vê. Verifique cada entrada dentro da ferramenta antes de agir com base nela:

```python
from chatflow_agent import tool

@tool
def update_email(user_id: int, new_email: str) -> str:
    """Update a user's verified email address."""
    if not isinstance(user_id, int):
        raise ValueError("user_id must be an integer.")
    if "@" not in new_email or "." not in new_email:
        raise ValueError("Invalid email format.")
    # Executar a atualização
    return f"Email updated for user {user_id}."
```

3. **Triagem Multiagente:** Utilize um agente inicial de triagem sem privilégios para classificar solicitações antes de roteá-las para agentes com permissões de escrita em bancos de produção.

## Segurança de Concorrência e Reentrância

<VersionBadge version="0.4.0rc1" status="prerelease" />

A partir da `v0.4.0rc1`, o `Runner` protege as sessões contra turnos reentrantes:
- Se código iniciado por um turno em execução (uma ferramenta, ou uma task ou thread que ela inicia: `create_task`, `gather`, `wait_for`, `TaskGroup`, `asyncio.to_thread`) chamar `runner.run_async` ou `runner.run` para a mesma sessão, o `Runner` levanta `ReentrantTurnError` imediatamente em vez de causar um deadlock. Use `Runner.spawn_turn()` para enfileirar um turno de acompanhamento.
- Requisições independentes para a mesma sessão são serializadas pela trava da sessão (por instância de store, ID de sessão e event loop).

Limitações conhecidas na v0.4.0rc1:
- Não há serialização entre instâncias de store sobre o mesmo arquivo, entre processos ou entre threads que executam seus próprios event loops.
- Uma ferramenta que aguarda um trabalho feito por uma task que não foi iniciada a partir do turno ainda pode causar deadlock se esse trabalho executar um turno da mesma sessão; aguardar uma task de `spawn_turn()` dentro do turno que a criou também causa deadlock.
- `clear_history()` e `delete()` (e, portanto, o `/reset` do Telegram) não são coordenados com turnos em execução além das garantias de reversão e de `SessionDeletedError`.
